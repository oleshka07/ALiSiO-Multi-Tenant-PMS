# Модуль `widget` — віджет бронювання

Форма бронювання, яку готель вставляє на власний сайт. До виділення в модуль
її код лежав у восьми місцях і питання «переписати чи прибрати віджет?»
означало ревізію третини системи. Тепер це локальне рішення.

## Межа

```
node scripts/check-boundaries.mjs widget
```

На момент виділення: **23 імпорти через фасад, 0 пробоїв**. Це означає, що
видалення каталогу `src/modules/widget/` ламає рівно 23 рядки імпортів і
нічого більше — жоден інший модуль не читає таблиці віджета і не тягнеться в
його нутрощі.

## Дві парадні двері

| Двері | Для чого |
|---|---|
| `@widget` | серверні хендлери. Тягне `better-sqlite3`, тому недоступний з `'use client'` |
| `@/modules/widget/ui/...` | React-компоненти. Клієнтський код бере їх напряму |

Це не виняток для віджета — так влаштований кожен модуль, і
`check-boundaries.mjs` рахує обидва шляхи як фасад.

## Що всередині

```
api/        13 хендлерів публічних ендпоінтів + аналітика (774 рядки)
ui/         BookingV2 (сучасна форма) + BookingIframePage (стара) + спільні
            переклади, локалі, типи, утиліти, два CSS
```

## Дві реалізації, обидві живі

| Реалізація | Маршрут | Розмір | Як віддається готелю |
|---|---|---|---|
| `BookingV2` | `/w/[siteSlug]` | 1 012 рядків + 2 094 CSS | `<script>` embed, `public/widget/native-*.js` |
| `BookingIframePage` | `/booking?site=slug` | 2 122 рядки + 2 596 CSS | `<iframe>`, вкладка «Віджет» у налаштуваннях сайту |

Це не помилка виділення — так було й до нього. Дві незалежні форми з власними
стилями, власними копіями типів і власним потоком бронювання. Яка з них
виживе — окреме рішення; обидві лежать в одному модулі саме щоб це рішення
можна було ухвалити, дивлячись на них поруч.

## Публічні ендпоінти — правило тенанта

Майже кожен маршрут тут **публічний**: його викликає сайт готеля, сесії немає,
є CORS. Тому тенант мусить приїхати в самому запиті — `siteId`, `siteSlug` або
`propertyId`.

**Публічний ендпоінт віджета ніколи не має права відкотитися на «перший
активний property».** Саме так виглядав витік: віджет чужого готелю показував
ціни й наявність першої організації в таблиці.

## Що лишилося поза модулем

- `public/widget/` — зібрані бандли (`native-bundle.js` 301 КБ, `embed.js`
  46 КБ). Next.js віддає `public/` з кореня, перенести не можна. Це артефакти
  збірки, не джерела.
- `src/app/api/widget/*`, `src/app/w/[siteSlug]`, `src/app/booking` — маршрути.
  Тонкі: імпорт із `@widget` і один рядок експорту. Маршрути живуть у
  `src/app/` за угодою Next.js.
- `src/app/app/(dashboard)/settings/booking-widget/`,
  `sites/[siteId]/_components/WidgetTab.tsx` — екрани налаштувань. Це UI
  дашборда, який налаштовує віджет, а не сам віджет.

## Чого тут немає

`useBookingWidget`, `BookingWidgetEmbed`, `BookingV2` лежали в
`src/modules/bookings/ui/` — увесь той каталог виявився віджетом і переїхав
цілком. У `bookings` не лишилося жодного посилання на нього.

`booking-source-widgets.handlers.ts` **не** переїхав, попри назву: це
випадальний список джерел бронювання у формі ручного заведення броні. Слово
«widget» у цьому коді означає інше.
