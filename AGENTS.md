# Правила роботи над цим проєктом

Стосується всіх — людей і агентів (Claude Code, Cursor, Copilot, будь-яких
інших). Цей файл читається **першим**.

## 1. Спершу прочитати

Перед першою зміною коду прочитайте:

| Файл | Про що |
|---|---|
| [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) | шари, модулі, модель тенантності, guard-и, перевірки |
| [docs/SECURITY-FINDINGS.md](docs/SECURITY-FINDINGS.md) | що вже ламалося тут і як це шукати |
| [docs/DEPLOY.md](docs/DEPLOY.md) | два середовища, спільний VPS, відкат |
| [docs/DECISIONS.md](docs/DECISIONS.md) | що вже вирішено і ким — щоб не питати вчетверте |

Це не формальність. Система мультитенантна: запит без обмеження за
організацією не падає з помилкою — він **тихо віддає або псує дані іншого
клієнта**. Половина знахідок у SECURITY-FINDINGS.md — це код, який виглядав
правильним.

## 2. Документація оновлюється разом зі змінами

**Правило.** Зміна, яка робить документацію неточною, не завершена, поки
документацію не оновлено. Це частина того самого коміту, а не наступна задача.

Що і коли:

| Ви змінили | Оновіть |
|---|---|
| нову таблицю, колонку, констрейнт | `docs/ARCHITECTURE.md` — розділ моделі даних |
| новий модуль або переніс код між модулями | `docs/ARCHITECTURE.md` — розділ шарів |
| новий guard, зміну правил доступу | `docs/ARCHITECTURE.md` — розділ особи запиту |
| новий публічний маршрут або префікс | `docs/ARCHITECTURE.md` — публічна поверхня |
| знайдену вразливість (навіть виправлену) | `docs/SECURITY-FINDINGS.md` — новий пункт |
| **нову родину guard-ів** | словник у `scripts/check-route-guards.mjs` — інакше перевірка оголосить захищені маршрути незахищеними |
| схему БД так, що змінилися типи | перегенеруйте `db/postgres/schema.sql` |
| кроки розгортання, скрипти, nginx | `docs/DEPLOY.md` |
| закриту фазу або аудит | `docs/ARCHITECTURE.md` — розділ «Стан і що далі» |
| вирізали модуль | тег `<модуль>-before-removal` + гілка `archive/<модуль>`, і рядок про це в `docs/ARCHITECTURE.md` |

Якщо під час роботи ви помітили, що документація вже розходиться з кодом —
виправте це, навіть якщо не ви її зламали. Неточний документ гірший за
відсутній: за ним ухвалюють рішення.

Якщо ви щось **свідомо не зробили** (обмеження, спрощення, відкладена
частина) — це теж пишеться в документацію, а не лише в чат. Через тиждень чат
ніхто не перечитує.

## 3. Інваріанти, які не можна порушувати

1. **Організація приходить із сесії.** Ніколи не з тіла запиту без перевірки і
   ніколи не з `SELECT ... LIMIT 1`.
2. **Кожна нова таблиця має `organization_id`** і індекс по ньому.
3. **UNIQUE на значенні, яке обирає людина, включає організацію.**
4. **Кожен маршрут проходить через guard.** Виняток — публічний, і тоді він
   доводить право іншим способом (токен, підпис, ідентифікатор орендаря в
   запиті), і це записано в `src/proxy.ts` разом із причиною.
   Тримає `scripts/check-route-guards.mjs --strict` у `npm run check`.
   **Своя перевірка сесії в тілі хендлера — не guard.** Вона встановлює
   особу, але не орендаря, тож на Postgres політики бачать порожню
   організацію: маршрут виглядає робочим і віддає порожній екран.
5. **Чужий id → 404, не 403.**
6. **`e.message` не йде клієнту.** Загальне повідомлення у відповідь, деталі —
   в `console.error`.
7. **Жодних секретів, PIN-ів, токенів і ключів у файлах, які комітяться.**
   Навіть тестових. GitHub сканує всі коміти.
8. **Публічний endpoint не має мовчазного дефолту.** Немає ідентифікатора
   орендаря — 400.
9. **Обчислену суму округлюємо перед записом** — `money()` з `@core/money`,
   а не `Math.round(x*100)/100` і не `.toFixed(2)`.
10. **`db/postgres/schema.sql` не редагується руками.** Це вивід
    `scripts/pg-schema.mjs`; рішення про типи — у мапі `OVERRIDE` всередині
    генератора. Генератор читає **локальну** SQLite, тому спершу переконайтесь,
    що вона свіжа: він відмовиться писати, якщо колонки зникають
    (`--allow-removals` — для свідомого видалення). Порядок колонок може
    перескочити між машинами — це косметика, позиційних `INSERT ... VALUES`
    у коді немає.
11. **Орендар належить зʼєднанню, а не запиту.** Усе, що ставить змінну
    сесії (`set_config`, `SET`), мусить піти тим самим зʼєднанням, що й
    наступний запит. Два `pool.query()` — це два різні зʼєднання.
12. **`INSERT` у scoped-таблицю НАЗИВАЄ `organization_id` явно.**

    Тут раніше стояло протилежне — «не пише руками, колонка має `DEFAULT` від
    контексту». Це було неправильно, і воно коштувало 23 місця. `DEFAULT` із
    `app.organization_id` — механізм **Postgres** (міграція 0005); у SQLite
    його немає й не буде, а SQLite стоїть на кожній машині розробника, під
    `npm run dev` і в тому завданні CI, яке піднімає застосунок. Рядок
    отримував NULL-орендаря беззвучно: `INSERT` відповідав 201, список
    повертався порожнім, у логах нічого — бо нічого й не ламалося. Рядок без
    орендаря це рядок, якого жоден орендар не бачить.

    Орендар береться з сесії, або підзапитом від рядка, на якому висить:

    ```sql
    INSERT INTO reservations (id, organization_id, property_id, …)
    VALUES (?, (SELECT organization_id FROM properties WHERE id = ?), ?, …)
    ```

    Підзапит кращий за змінну там, де сесії немає (вебхук, синк каналу,
    гостьовий шлях): він не може розійтися з обʼєктом, від якого походить.

    Тримає `scripts/check-insert-tenant.mjs --strict`.

    Прапорці при цьому пишуться `TRUE`/`FALSE`, не `1`/`0`: літеральна
    одиниця в колонку `BOOLEAN` відхиляється Postgres.
13. **Перевірка, яка не знайшла рядка, відмовляє, а не дозволяє.** Половина
    знахідок розділу 12 у SECURITY-FINDINGS.md — це «немає рядка, отже
    обмежень немає» на порожньому контексті орендаря.
14. **Посилання-перепустка ставить токен на зʼєднання, а не додає `WHERE`.**
    Сторінка, яку відкривають без сесії (гостьовий портал, партнерський звіт),
    читає свій рядок через `runWithPublicToken` — політика звіряє токен сама.
    Одне налаштування `app.public_token` на всі такі таблиці; нове
    `app.*_token` не заводиться, змінюється колонка в `PUBLIC_TOKEN_READ`
    (`scripts/pg-schema.mjs`). Прочитавши рядок, далі йдемо звичайним
    `runWithOrganization` — вікно, у якому токен щось значить, шириною в один
    запит.
15. **Заселеність міняє ціну, ніколи не категорію.** Той самий номер для
    однієї особи і для двох — один рядок номерного фонду і дві ціни
    (`price_occupancy`). Категорія «одномісний» змусила б готель вести два
    списки номерів на один набір кімнат.
16. **Скільки коштує ніч — питає лише `priceNights()`** із
    `pricing/data/nightly-price.ts`. Свій цикл по днях не пишеться. Їх було
    чотири, і в кожному стояв `let dayPrice = 2500` — число одного клієнта,
    тихо виставлене будь-кому, хто бронював наступним.
17. **Ціни, якої немає, не існує.** Ніч, яку не покриває жодне джерело,
    називається (`quote.missing`) і не продається. Вигадане число — це
    бронювання за ціною, якої готель ніколи не називав.
18. **Ставка податку обирається за датою ПОСЛУГИ** і записується на
    нарахування числом. Назад таблиця ставок ніколи не читається — інакше
    фактура 2026 року переписалася б після зміни закону.
19. **Текст на документі — мовою юрисдикції, не оператора.** `documentLanguage()`
    і `chargeName()`, ніколи `t()`. Тримає `check-i18n-leak.mjs`.
20. **Дані, які клієнт може змінити сам, не бувають літералом у коді.** Ціна,
    назва послуги, текст пропозиції, відсоток угоди — рядок у базі з
    `organization_id`. Ознака порушення: константа, де поруч ціна і назва
    продукту. Тримає `check-no-tenant-names.mjs` (список `FORBIDDEN_IN_CODE`),
    але лише для вже відомих маркерів — решту ловить це правило. Приклад:
    `GIFT_CARD_TEMPLATES` — шість ваучерів одного кемпінгу з цінами й
    продуктами, які бачив кожен готель на сервері (INC-006).
21. **Схема читається з `origin/main`, ніколи з робочої копії.**

    ```bash
    git show origin/main:src/lib/db.ts     # так
    cat src/lib/db.ts                      # ні
    ```

    Робоча копія — це чиясь гілка, і вона може бути якою завгодно старою.
    2026-08-31 сесія два дні складала план перебудови ядра, вимірявши
    схему на гілці, що відстала на 411 комітів: «глобальні `settings`»,
    `investors`, `bank_statements` — усе це справді там було, п'ять тижнів
    тому. Висновки довелося перевипускати.

    **І перш ніж робити висновок з ІСТОРІЇ — перевірити, чи вона повна.**
    Клон веб-сесії обрізаний:

    ```bash
    git rev-parse --is-shallow-repository   # true → історії немає локально
    git fetch --unshallow                   # перед будь-яким merge-base
    ```

    Того самого дня друга сесія — перевіряючи першу — назвала межу
    обрізання `.git/shallow` коренем дерева, не знайшла спільного предка й
    оголосила дві гілки різними продуктами. Насправді корінь у них один.
    В обрізаному клоні `git merge-base`, `rev-list --count` і «корінь»
    означають не те, що здається: перше повертає порожньо, друге —
    занижене, третє — просто місце обриву.

    Обидві помилки одного класу: **виміряно точно, але не те.** Тримає
    `.claude/hooks/session-start.sh` — він каже про обидва стани на старті.

22. **Юрисдикція — це модуль. Ядро нейтральне.**

    Продукт робиться для Європи **І** України одночасно. Усе, що специфічне
    для однієї країни — ПРРО і рядок 11 фіскального чека, турзбір за
    правилами ДПС, Дія-чек-ін, KSeF, e-Factura, TSE — живе окремим ключем
    реєстру (`fiscal_ua`, `fiscal_pl`, `fiscal_de`) і вмикається лише тим
    клієнтам, кому потрібне. Зразок уже в коді: `fiscal_de`, дефолт OFF.

    Ядро — `fees_taxes`, `fin_tax_rates`, `applyFees()` — не знає назв
    юрисдикцій. Воно каже, **що це за гроші**, а не як їх показати в чеку
    конкретної країни. Різницю видно на прикладі:

    | Ядро | Модуль юрисдикції |
    |---|---|
    | `collected_for = 'authority'` — гроші не готелю | «рядок 11 чека, без ПДВ» — `fiscal_ua` |
    | `applies_to = 'adults'` — дітей звільнено | «до 18 років за ПКУ ст. 268» — `fiscal_ua` |
    | ставка з датою в `fin_tax_rates` | «знижена ставка на проживання» — модуль країни |

    **Ознака порушення: назва країни, її закону або її документа в імені
    таблиці, колонки чи значення CHECK.** `tax_type = 'tourist_tax'` виглядає
    нейтрально і не є ним: воно кодує одну юрисдикцію в ядрі, і наступний
    клієнт з іншої країни отримає колонку, яка йому бреше.

    Куди класти нове: якщо правило можна пояснити, не називаючи країну, — це
    ядро. Якщо не можна — це модуль.

23. **Перед питанням до власника — журнал, код, дослідження. У такому порядку.**

    Питання бувають трьох видів, і лише один з них його:

    | Вид | Приклад | Що робити |
    |---|---|---|
    | **уже вирішено** | «нарощувати `price_calendar` чи перейменувати» | `docs/DECISIONS.md` |
    | **факт** | «чи входить збір у `total_price`» | `git show origin/main:…`, `docs/research/`, `docs/vendor/channex/` |
    | **гроші, ринок, смак** | «скільки коштує тариф», «чи віддаємо сайт безкоштовно» | **спитати** |

    31.08.2026 сесія спитала про `price_calendar` вчетверте: рішення на той
    момент було ухвалене тричі — вона сама його рекомендувала, власник
    погодився, дослідницька сесія підтвердила. Того ж дня вона спитала, чи
    входить турзбір у `total_price`, — а в `reservations` уже лежали
    `city_tax_amount`, `city_tax_included`, `city_tax_paid`, у
    `booking_sources` — `city_tax_included_default`, і був готовий звіт.
    Відповідь була в коді, а не у власника.

    Причина не в конкретній сесії: **рішення ухвалювались у чаті й не
    потрапляли туди, куди агент дивиться перед роботою.** Чат закінчується,
    контекст обнуляється, питання відроджується, власник платить за це
    вдруге.

    Тому рішення живе в `docs/DECISIONS.md` — рядком, із датою і посиланням
    на обґрунтування. **Запис туди — частина того самого коміту**, що й код,
    так само як документація (§2). Рішення, якого там немає, вважається
    неухваленим; рішення, яке там є, не перепитується — його можна лише
    свідомо скасувати, дописавши в той самий рядок «скасовано ДД.ММ, бо…».

24. **Суттєва зміна починається з ЧЕРВОНОГО гейта.**

    Порядок такий, і він не переставляється:

    1. написати перевірку, яка впаде, якщо зміна буде неправильною;
    2. **побачити її червоною** — на нинішньому коді, або зламавши код
       навмисно, якщо вона зелена від початку;
    3. і лише тоді робити зміну, і побачити її зеленою.

    **Перевірка, яка ніколи не була червоною, не доводить нічого.** Вона
    доводить лише, що вона запускається. Пропущений крок 2 — це не економія
    часу, це заміна доказу на враження.

    Суттєва — це зміна схеми, грошей, доступу, наявності або будь-чого, що
    ламається мовчки. Дрібна правка тексту гейта не потребує.

    За одну сесію 31.08.2026 крок 2 знайшов три речі, яких не знайшло б
    читання:

    | Що | Як знайшлося |
    |---|---|
    | `check-unit-join.mjs` мав діру рівно того класу, який ловить: коли перший джойн уже виправлений, INNER у ланцюжку за ним не перевірявся **ніколи** | спроба завалити власний гейт чотирма способами; третій пройшов |
    | `check-isolation.mjs` роками тверджував «готель без фічі не має відкритого публічного запису» — і після зміни дефолту твердження стало беззмістовним: воно не впало б, якби варта справді зламалась | запуск; `tsc` і `npm run check` мовчали обидва |
    | перебудова таблиці в SQLite мовчки знесла всі індекси `reservations`, включно з УНІКАЛЬНИМ на гостьовий токен | `pg-schema.mjs` — індекси зникли з diff-у Postgres-схеми |

    **Наслідок, важливіший за саме правило.** Гейт, який перестав уміти
    ставати червоним, гірший за відсутній: відсутній нічого не обіцяє, а цей
    доповідає про безпеку. Тому перевірка, яку зачепила зміна — дефолт,
    назва ключа, форма даних, — перевіряється на червоність **заново**, а не
    вважається робочою тому, що вона зелена.

## 4. Перед комітом

```bash
npx tsc --noEmit                        # 0 помилок
npm run check                           # доменні self-check'и
npm run check:i18n                      # покриття, мертві записи, форми множини
npm run check:unwrapped                 # кирилиця без t() — новий текст, який не перекласти
npm run check:i18n-leak                 # мова оператора в документах, листах, інтеграціях
node scripts/check-no-tenant-names.mjs  # жодного бізнесу клієнта в коді
node scripts/audit-dead-data.mjs        # таблиці й колонки, яких ніхто не читає
```

Міграції Postgres накочує `deploy/deploy.sh` — між збіркою і рестартом, через
`deploy/migrate.sh` (журнал у таблиці `schema_migrations`). Руками це більше
робити не треба; `./deploy/migrate.sh prod --list` показує, що чекає.

Перед підключенням клієнта — ще й перевірка **живої** бази:

```bash
DATABASE_URL=… node scripts/check-deployed-db.mjs
```

Вона питає базу про відбитки кожної міграції. Пропущена міграція не падає на
деплої: вона проявляється як мовчазна відсутність функції (0007 — увесь
гостьовий портал у 404; 0008 — те саме, якщо код уже ставить
`app.public_token`, а політика в базі досі чекає `app.guest_token`).

`npm run check` містить і гейти, кожен з яких написаний після того, як те
саме вже зламалося:

| `search` | розділ пошуку без права, провайдер без орендаря, мертва кнопка в шапці |

Останній тримає §2 цього ж файлу. Правило «документація оновлюється разом зі
змінами» існувало з самого початку і протрималося рівно доти, доки про нього
не забули на десять комітів поспіль: за тиждень зʼявилися фоліо, фактури,
сторно, ставки ПДВ, цінова матриця, правила каналів і два нові гейти — і
жодного рядка в `docs/`. Правило, про яке нікому не нагадують, — це не
правило.

**Чому саме `check-no-tenant-names` тепер блокує.** Це єдина перевірка, яка
ловить «підправлю трошки під цей готель»: назву, домен, IČO, словник
категорій. Вона існувала, але запускалась лише тоді, коли хтось згадував — і
за перший же тиждень пропустила згадку, яка в'їхала з новим скриптом. Різниця
між гейтом і скриптом, який треба пам'ятати, — це різниця між «неможливо» і
«поки що не сталося».
Кожен із них написаний після того, як відповідна річ уже зламала прод.

Те саме бігає в CI на кожен push — `.github/workflows/checks.yml`. Це не
заміна прогону в себе, а страховка від того, що над проєктом працюють
паралельно: `provisionOrganization` втратив `await`, коли `core` переїхав
на асинхронний шов, і `provision-org.mjs` два дні друкував `undefined`
замість ідентифікатора організації, бо ніхто випадково його не запустив.

CI гейтить лише те, що зараз проходить детерміновано. `npm run lint` там
свідомо немає: він видає ~5000 успадкованих зауважень, а червона збірка,
яку ніхто не може полагодити, — це збірка, яку всі вчаться ігнорувати.

Окрема робота `live` піднімає зібраний застосунок на **порожній** базі,
створює клієнта через `provision-org.mjs`, і на ньому ганяє
`check-isolation.mjs` та e2e. Саме там ловляться речі, яких статика не
бачить: пропущений `await` у місці, де результат читається трьома
рядками нижче, і биті посилання на публічному сайті.

Якщо зміна торкається **схеми** (`src/lib/db.ts`) — обов'язково:

```bash
npm run build:win
node scripts/check-fresh-schema.mjs            # новий клієнт = ця база
node scripts/check-fresh-schema.mjs --settles  # і схема стала з першого проходу
```

Другий режим питає інше й не потребує «старої» бази: застосунок піднімається
**двічі на одній порожній теці**, і два знімки звіряються. Мігратор, який на
другому проході дає інше, ніж на першому, означає, що новий клієнт і той
самий клієнт після першого перезапуску контейнера мають різні схеми. Саме так
три індекси `accruals` існували лише в тих, хто вже перезавантажувався. Цей
режим бігає в CI; звичайний — ні, бо в чистому клоні нема з чим порівнювати.

**Порівнюються таблиці, колонки й ІНДЕКСИ** — останні за означенням, а не за
іменем. `CREATE UNIQUE INDEX` окремим рядком це ОБМЕЖЕННЯ, а не пришвидшення:
`idx_reservations_guest_token` не дає двом гостям отримати одне посилання.
Відсутній або послаблений, він нічого видимого не ламає — він просто перестає
забороняти.

Міграції тут написані як «оновити з попереднього стану», тому `ALTER TABLE
ADD COLUMN` легко опиняється **вище** за `CREATE TABLE` тієї самої таблиці: на
порожній базі воно тихо падає, і новий клієнт не отримує колонки, яку код
читає. Додаєш колонку — додай її **і в CREATE, і в ALTER**. Видаляєш — прибери
створення, а не дописуй DROP у кінець.

**Те саме стосується ІНДЕКСІВ, і це легше проґавити.** Індекс, дописаний лише
в міграцію, є в мігрованому середовищі й відсутній у нового клієнта — а
`check-fresh-schema` цього не бачить за означенням: він звіряє SQLite із
SQLite, де індексу бракує однаково з обох боків. Видно лише
`check-schema-drift` на справжньому Postgres. Так пройшов
`idx_reservations_unassigned` (0051) — його не було в `src/lib/db.ts`.

**Наявність констрейнта перевіряється за ОЗНАЧЕННЯМ, а не за іменем.**
`ADD CONSTRAINT IF NOT EXISTS` у Postgres немає, тож міграція питає каталог —
і питати треба `pg_get_constraintdef(oid) LIKE 'FOREIGN KEY (col) REFERENCES%'`,
а не `conname = '…_1'`. Ім'я довільне: на свіжій базі той самий ключ уже
створив `db/postgres/schema.sql` під СВОЇМ іменем, бо генератор нумерує їх у
своєму порядку. Сторож за іменем не знаходить нічого й додає **другий такий
самий** ключ — новий клієнт отримує не «без констрейнта», а дубльований
констрейнт під двома іменами. Ловить `check-schema-drift.mjs`, і зловив:
0048, 0052 і 0053 давали разом сім таких пар.

**Перебудова таблиці в SQLite зносить її індекси разом із нею, і мовчки.**
`DROP TABLE` + `RENAME` — єдиний спосіб змінити тут констрейнт, і за один
такий прохід уже двічі зникало те, що мало забороняти: УНІКАЛЬНИЙ індекс на
гостьовий токен `reservations` і три індекси `accruals`, зокрема по
`organization_id`. Тому перебудова **знімає `sql` індексів до підміни,
повертає їх після і звіряє лічильник** — інакше вона мовчки віддає базу без
захисту, який у ній начебто є.

Останнє — не косметика. Назва готелю в коді означає, що хтось інший
побачить чужий бренд або заплатить на чужий рахунок. Дані клієнта живуть
у базі.

Якщо зміна торкається доступу до даних, ще й:

```bash
npm run dev &
node scripts/check-isolation.mjs
node scripts/audit-tenant.mjs
node scripts/audit-routes.mjs
node scripts/audit-by-id-scope.mjs   # запит по id з URL без орендаря — список
```

Останній має два режими. Без прапорця — звіт: 59 місць у 15 файлах
(2026-08-29), і це НЕ 59 дірок — у більшості власність доведена вище в тому
ж хендлері або id приходить із сесії. З `--strict` він бігає в `npm run
check` храповиком: стеля кожного файла зафіксована, нове порушення валить
збірку, виправлене вимагає опустити стелю. Тобто список читається очима
поступово, а межа тримається машиною. Клас — INC-010.

Перед push складних змін (нові маршрути, схема, конфіг розгортання) — повний
build **і прогін по маршрутах**:

```bash
npm run build:win
node scripts/check-fresh-schema.mjs   # схема нового клієнта = цій базі
npm run start &
node scripts/smoke-routes.mjs                       # усі GET
SMOKE_SESSION=<cookie> node scripts/smoke-writes.mjs POST   # і записи
SMOKE_SESSION=<cookie> node scripts/smoke-writes.mjs PUT
SMOKE_SESSION=<cookie> node scripts/smoke-writes.mjs PATCH
```

`smoke-writes` будує тіло з того, що хендлер сам деструктурує, а значення
бере за змістом назви поля — id з бази, дати, суми, а для enum-полів
значення, яке дозволяє CHECK. Він **пише**: ганяти лише на тестовій базі.

Читати його вивід треба обережно: «відмовили» — це не результат, це роути,
до яких він не дістався (валідація, права, 404). Серед 5xx більшість — його
власне синтетичне значення, яке база правильно відкинула; справжнє видно за
текстом помилки в логу сервера, а не за статусом.

Прогін обовʼязковий, якщо ви чіпали SQL. `tsc` не бачить помилок у запитах —
SQL це рядок, — тож запит із неіснуючою колонкою компілюється, збирається,
проходить усі аудити й віддає 500 на кожен виклик. Саме так увесь список
номерів (`/api/units`) був зламаний невідомо скільки часу.

Прогін робіть по production-збірці: dev-сервер компілює кожен маршрут при
першому зверненні і на 183 маршрутах помирає від нестачі памʼяті.

Нова нетривіальна логіка лишає по собі одну запускну перевірку — `.check.ts`
поруч із кодом, підключений у `npm run check`. Без фреймворків.

**Перевірка, яка шукає щось у вихідному коді, спершу вирізає коментарі** —
інакше вона рахує власну документацію і приклади того, що вже виправлено.
Тричі за одну сесію: `currency.check` ловив свій же приклад
`row.currency || 'CZK'`, `invoicing.check` — свій список таблиць обліку, а
потім історичну згадку видалених констант у чужому коментарі.

## 5. Розгортання

Сервер спільний з іншими проєктами. Детально — у [docs/DEPLOY.md](docs/DEPLOY.md),
але коротко:

- `deploy/setup-vps.sh` — **лише для порожнього сервера**. Він вмикає ufw і
  перезаписує конфігурацію nginx. Скрипт сам відмовляється працювати, якщо
  бачить чужі сайти або активний фаєрвол.
- `deploy/add-site.sh` — для сервера, де вже щось є. Додає лише свої
  server-блоки й сертифікати, більше нічого не чіпає.
- `deploy/deploy.sh beta|prod` — розгортання. Спершу beta, перевірка, потім
  prod.
- `deploy/status.sh prod|beta`, `deploy/logs.sh prod|beta` — стан і логи
  одного середовища, без згадування імен контейнерів.
- `deploy/run-cron.sh prod|beta /api/cron/<name>` — запуск планової роботи
  застосунку з секретом із env-файла, і головне — читання ТІЛА відповіді:
  `success:false` або ненульовий `failedOrganizations` це вихід 1, а не
  «крон відпрацював». GDPR-ретенція (`/api/cron/gdpr-retention`) стоїть у
  розкладі `setup-backup-cron.sh` о 04:40 — після нічного дампа, щоб
  невдале знеособлення мало куди відкотитись.
- `deploy/backup.sh`, `deploy/check-backup-age.sh`, `deploy/restore-test.sh`
  — щоденний дамп із заливкою у сховище поза сервером (ключ лише на запис),
  контроль свіжості з алертом, репетиція відновлення з виміром RTO. Розклад
  ставить сам `deploy.sh`; разове налаштування сховища — docs/DEPLOY.md
  → «Бекапи поза сервером».
- `deploy/check-disk.sh` — диск ≥75% → алерт (щогодини з крона);
  `deploy/verify-backup-key.sh` — доказ, що ключ сховища лише на запис:
  запис проходить, читання й видалення відмовляють;
  `deploy/check-oom.sh prod|beta` — чи вбивало ядро контейнер за пам'ять
  (OOMKilled, рестарти, стелі `mem_limit`) і чи має кожен контейнер
  restart-політику, з якою переживе ребут хоста; лише читає;
  `deploy/apply-db-limits.sh prod|beta` — свідоме перестворення
  postgres-контейнера, щоб застосувати `mem_limit` (деплой сервіс бази
  навмисно не чіпає — він під profiles); відсутній `PG_MEM_LIMIT` дописує
  в env-файл сам (ідемпотентно), спершу перевіряє, що налаштування
  Postgres вкладаються в ліміт, знімає дамп і вимагає НАБРАТИ назву
  середовища — Enter не досить, бо команди, вставлені блоком, відповіли б
  самі за себе: ~10–30 с простою бази; наприкінці звіряє фактичний ліміт
  з очікуваним (розбіжність = вихід 1);
  `deploy/smoke.sh prod|beta` — дим по живому середовищу (health, логін-401,
  публічна головна, бандл) — deploy.sh ганяє його сам, руками — для
  перевірки поза деплоєм;
  `deploy/list-tenants.sh prod|beta` — read-only інвентар бази: організації
  з лічильниками і, головне, ІМЕНА категорій/типів/послуг — спадок видно в
  іменах, не в цифрах;
  `deploy/purge-tenant.sh prod|beta|local <slug>` — повне знесення одного
  орендаря: показує що видалить, вимагає набрати slug, знімає дамп, видаляє
  в одній транзакції всі ~60 тенантних таблиць (список з information_schema,
  нова таблиця потрапляє під ніж сама) і ДОВОДИТЬ нуль рядків — інакше
  відкат, напіввидаленого орендаря не існує; `local` — репетиція на стенді
  з AGENTS §7;
  `deploy/drill-health.sh prod|beta` — репетиція відмови БД для
  `/api/health` (стоп → 503 → старт → 200). **Зупиняє базу** на секунди:
  інструмент оператора, не сесії; на проді — лише свідомо.

**Оператору не диктуються разові команди на сервер. Немає скрипта — спершу
створюється скрипт.**

## 7. Постгрес: що перевірити перед тим, як казати «працює»

Прод і бета на Postgres із 2026-08-07/08. Це змінює те, як виглядає помилка:
запит без контексту орендаря там не падає з винятком — він **тихо повертає
порожнє** (читання) або відхиляється політикою (запис). Тобто типова
поломка виглядає як «функція зникла», а не як помилка в коді.

Тому:

- **`npm run check` і `tsc` не доводять, що функція працює.** SQL — це
  рядок; політика — це поведінка бази. Обидва мовчать.
- **PGlite у перевірках — одне зʼєднання.** Усе, що ламається лише на пулі,
  там не відтвориться. Такі речі перевіряються окремо
  (`pool-tenant.check.ts`) або на справжньому сервері.
- **Справжній Postgres піднімається локально за хвилину** і ловить те, чого
  не бачить ніщо інше:

  ```bash
  su postgres -c "initdb -D /tmp/pg/data -U alisio --auth=trust"
  su postgres -c "pg_ctl -D /tmp/pg/data -o '-p 55432 -k /tmp/pg' start"
  psql -h /tmp/pg -p 55432 -U alisio -c "CREATE DATABASE alisio_local"
  psql -h /tmp/pg -p 55432 -U alisio -d alisio_local -f db/postgres/schema.sql
  # усі міграції по черзі — CI робить так само, і саме тут ловляться ті,
  # що не переживають schema.sql
  for m in db/postgres/migrations/*.sql; do
    psql -h /tmp/pg -p 55432 -U alisio -d alisio_local -v ON_ERROR_STOP=1 -f "$m"
  done
  psql -h /tmp/pg -p 55432 -U alisio -d alisio_local -f db/postgres/rls-check.sql
  ```

  **Далі — роль без суперправ, і застосунок ходить нею.** Це не деталь:
  `initdb -U alisio` робить `alisio` **суперкористувачем**, а суперкористувач
  обходить RLS повністю — `FORCE ROW LEVEL SECURITY` на нього не діє. На такій
  базі кожна політика мовчить, і перевірка ізоляції показує зелене на будь-якому
  коді, включно зі свідомо зламаним. Так уже сталося 2026-08-28: «чужий готель
  бачить чужі дати» виявилось властивістю стенда, а не коду.

  ```bash
  psql -h /tmp/pg -p 55432 -U alisio -d alisio_local <<'SQL'
  CREATE ROLE alisio_app LOGIN;
  GRANT CONNECT ON DATABASE alisio_local TO alisio_app;
  GRANT USAGE ON SCHEMA public TO alisio_app;
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO alisio_app;
  GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO alisio_app;
  SQL

  # застосунок — ЦІЄЮ роллю, не власником
  DB_DRIVER=postgres \
  DATABASE_URL="postgresql://alisio_app@/alisio_local?host=/tmp/pg&port=55432" \
  npm run start
  ```

  Ім'я `alisio_app` — те саме, що в `deploy/to-postgres.sh`; сам `deploy`
  ходить нею ж, тому локальний стенд і прод відповідають однаково.
  `provision-org.mjs` і засів даних лишаються за власником: вони створюють
  готелів, тобто працюють поза орендарем за визначенням.

  Далі — **два** готелі через `provision-org.mjs`, і кожне твердження
  перевіряється з обох боків: свій бачить своє, чужий не бачить нічого.
  Один готель не доводить нічого: усе, що зламано, з ним виглядає цілим.

  Читати `SELECT` під власником схеми теж не можна — `FORCE ROW LEVEL
  SECURITY` діє й на нього, тож без орендаря він бачить порожнечу. Щоб
  подивитись базу «згори» (перевірити, що засів ліг), додайте
  `-c "SET row_security = off"` окремим `-c` перед запитом.
