Завдання: контрольний аудит. Перевір, чи захисні механізми пережили роботу
з часу останнього аудиту (останній запис реєстру інцидентів у
docs/SECURITY-FINDINGS.md — точка відліку), чи процес реально дотримувався,
і чи не з'явилося нового дрейфу. Ти аудитор, не автор: не вір документації,
вір фактам. Кожен висновок підкріплюй доказом: шлях до файлу, номер рану CI,
дата, вивід команди.

БЛОК 1. Чи живі замки
1. Хуки: чи виконувані файли в .claude/hooks/ (і на диску, і в git-індексі —
   git інколи губить біт). Потім живий тест у ЦІЙ сесії: спробуй
   git push --force origin main і редагування db/postgres/schema.sql.
   Обидва мають відмовити. Процитуй відмови дослівно.
2. Чи не ослабили захист: git log --oneline -- .claude/
   .github/workflows/deploy.yml .github/workflows/checks.yml з моменту
   попереднього аудиту. Кожну зміну в хуках і гейтах назви і поясни,
   навіщо вона була. Зміна «вниз» без запису в SECURITY-FINDINGS — провал.
3. Контекст: чи в пам'яті сесії і CLAUDE.md, і AGENTS.md. Якщо AGENTS.md
   немає — імпорт @AGENTS.md зламано, полагодь.

БЛОК 2. Чи дотримувався процес
4. git log main з моменту останнього аудиту: чи всі зміни пройшли через
   beta (merge-коміти або підтверджені бета-деплої). Кожен коміт повз
   бету назви.
5. Стан зараз: чи main не попереду beta (git rev-list --count --no-merges
   origin/beta..origin/main має бути 0).
6. Гейти порядку гілок у deploy.yml — негативний тест. Прожени логіку
   «prod ships only what beta has seen» на sha, якого немає в origin/beta
   (git commit-tree дає безпечний фіктивний коміт), і покажи, що крок
   падає. Знайди останнє живе спрацювання гейта «prod ships only what beta
   has RUN» у ранах deploy.
7. Храповики: базлайни в check-boundaries.mjs і currency.check.ts з моменту
   аудиту. git log по файлах гейтів. Підняття базлайну = обхід — назви
   коміт і причину. Живий прогін: якщо пробоїв поменшало — звузь базлайн.

БЛОК 3. Чи жива пам'ять
8. ARCHITECTURE §8: поточний стан чи стан минулого аудиту? Звір числа з
   живими прогонами (boundaries, кількість таблиць у генераторі), не з
   пам'яттю.
9. Правила, що живуть лише в розмовах: переглянь зміни коду за період на
   неочевидні рішення (обхідні шляхи, «не чіпати», хитрі умови), яких немає
   ні в AGENTS.md, ні в ARCHITECTURE, ні в .claude/rules/. Список
   кандидатів покажи людині ПЕРЕД додаванням.
10. SECURITY-FINDINGS: чи були за період поломки, відкати або червоні смуги
    CI, які мали стати записом, але не стали? git log --grep і рани CI.
    Кожен новий інцидент — номер у реєстрі INC.

БЛОК 4. Чи працює те, що має працювати саме
11. Бекапи: час останнього щоденного дампа, останнього off-site маркера,
    останнього недільного restore-test (./deploy/check-backup-age.sh,
    ./deploy/status.sh). З сесії сервер недоступний — сформулюй точні
    команди оператору і зістав його відповіді.
12. Негативний тест write-only: ./deploy/verify-backup-key.sh — запис МУСИТЬ
    пройти, читання і видалення МУСЯТЬ відмовити.
13. /api/health: репетиція відмови БД — ./deploy/drill-health.sh beta
    (оператор; на проді лише свідомо).
14. Контейнери: ./deploy/check-oom.sh prod і beta — чи не було OOMKilled.

ФОРМАТ ЗВІТУ:
- таблиця: номер, пункт, статус ОК/ПРОВАЛ/ЗРОБЛЕНО ЗАРАЗ, доказ
- окремо: порушення процесу, якщо були, без пом'якшень
- окремо: що зробити руками, якщо є
- наприкінці два речення простими словами: чи можна довіряти системі
  і що одне найслабше зараз
