# Міграція готелю з Winhotel.MX + міст DIRS21

Плейбук виходу на німецький ринок: як забрати готель, що працює на
Winhotel.MX (CDSoft) із channel manager-ом DIRS21, без розриву онлайн-продажів.
Клієнт тут не називається навмисно — див. правило про імена клієнтів в
[AGENTS.md](../AGENTS.md) §4 (`check-no-tenant-names.mjs`); конкретика
клієнта живе в задачах, не в репо.

Статус: **дослідження завершено, реалізація не почата.** Дата: 2026-08.

---

## 1. Рішення

**Жива двостороння інтеграція з Winhotel.MX не робиться.** Публічного API
немає («відкрита API-шнітштеле» з V.24 — закрита, за контактом з CDSoft,
тобто залежність від вендора, якого клієнт покидає). Дані системи лежать у
локальному Firebird-файлі (`c:\winhotelmx\daten\winhotel.fdb`) — читаються
стандартними інструментами без участі CDSoft.

Стратегія — **міграція з дзеркальним перехідним періодом**:

1. дані витягаються з Firebird (структура, гості, брони, ціни, послуги);
2. наш адаптер DIRS21 замінює Winhotel як «PMS-кінець» каналу — усі
   OTA-підключення готелю (Booking.com, HRS, власний IBE «DIRS21 One»)
   лишаються незмінними, перемикається лише PMS-інтерфейс;
3. до перемикання наша система працює як read-only дзеркало їхньої бази зі
   щоденною звіркою.

Чому не «перевести готель на Hostex»: Hostex не має німецьких каналів (HRS)
і не замінює IBE на сайті готелю; DIRS21 — лідер DACH, його заміна — окремий
ризиковий проєкт без потреби.

## 2. Джерельна система: факти

| | |
|---|---|
| Продукт | Winhotel.MX Frontoffice, V.25 (CDSoft, Кемптен) |
| Тип | on-premise Windows, класичний двошаровий клієнт |
| БД | Firebird, один файл `winhotel.fdb`; схему дізнаємось з `RDB$RELATIONS` |
| Канали | DIRS21 через їхній PMS-інтерфейс V3 (двосторонній: ARI туди, брони сюди) |
| Драйвери для нас | `node-firebird` (pure JS) або `node-firebird-driver-native` |

Доменні поняття Winhotel, які треба вміти прийняти при імпорті:

- **Angebot vs Reservierung** — пропозиція (квота) до бронювання; у нас
  лягає на `reservations.status = 'tentative'`.
- **Leistungen** — послуги окремими рядками до брони (Übernachtung,
  Frühstück €/особа/ніч, гараж) — у нас `additional_services` +
  майбутні `invoice_line_items` (див. §4).
- **Buchungs-Segmente** (DIRS21 / direct / телефон) → `booking_sources`.
- **AGB/Storno-політики** на брони → `rate_plans.cancellation_policy`.
- **Anz. Erw. / Jug. / Kinder** — три вікові групи дітей (вікові межі —
  з налаштувань клієнта).
- **Mandant** — у базі може бути кілька юросіб; перевірити перед імпортом.
- Категорії кімнат (типові коди DZD/DZK/SD/EZ/APP) → `unit_types.code`,
  ціна за категорію → `price_calendar (unit_type_id, date)` — модель збігається.
  Категорії бувають прив'язані до продуктової лінійки (у пілота остання
  літера коду: D = Design, K = Klassik — стилі поверхів, не корпуси),
  тобто «той самий» DZ у двох лінійках — дві категорії з різними цінами.
- **Цінова модель пілота** (з офіційних прайсів; типова для німецького
  приватного готелю): 2 сезони (Neben/Hauptsaison) × ціна за заселеність
  (1/2/3/4 особи) × **знижка за тривалість** (ab 3 Nächte) + Aufbettung
  (диван-ліжко, фікс за особу) + дитячі правила (у ліжку батьків
  безкоштовно; сніданок дітям до 6 р. безкоштовний). Отже day-1 модель
  цін: (категорія, сезон/дата, заселеність, LOS-поріг).
- **Сніданок ділиться на їжу і напої** (Speisen/Getränke, різний ПДВ):
  у пілота 15 € = 12 + 3. Пропорція — налаштування організації.
- **OTA-ціна — похідна формула**: (стандартна ціна + сніданки) × націнка
  (у пілота +15%). Це правило деривації тарифу, не окремий прайс.
- **Авторозщеплення OTA-суми — головний щоденний біль рецепції**: з
  Booking приходить одна сума, персонал руками ділить її на
  Übernachtung / Frühstück-Speisen / Getränke для бухгалтерії, помилки
  коштують пів дня і псують рахунки. Наш імпорт бронювань робить це
  розщеплення автоматично за правилами організації (див. §4.12).
- **Angebot-блоки (контингенти)**: весілля/групи — блок номерів під
  ключове слово, гості викуповують кімнати з блоку окремими дзвінками
  до дедлайну. Лягає на `reservation_groups` + `tentative`.
- **Побічні ресурси, що бронюються як номери**: паркомісця гаража
  (10 €/ніч/місце), зал (погодинна оренда — окремий бізнес з договорами),
  дешеві апартаменти поза основною сіткою. У сітці Winhotel це
  псевдо-номери 9xxx — при імпорті мапляться на окремі unit_types з
  прапорцями видимості.
- **Firmenraten** — договірні ціни для десятків фірм/установ
  (у Winhotel — довідник Vermittler/Debitoren; на практиці — ще й
  паперові шпаргалки на рецепції). При імпорті звірити обидва джерела.
- **Anzahlung** (депозит) — окреме поле на броні; на cutover відкриті
  депозити переносяться як передоплати.
- **Debitoren-Nummer** на броні — номер дебітора для бухгалтерії
  (готує ґрунт під DATEV-експорт, §4 п.7).
- **Kassen-/Telefonverbund** — зв'язка з касою і телефонною станцією
  (тарифи дзвінків на рахунок номера). З'ясувати, чи активна.

## 3. DIRS21: міст, який зберігає продажі

- Оператор — TourOnline AG; PMS-інтерфейс **V3**, XML по HTTPS
  (`pmsif.dirs21.de`). Передається: доступність, ціни, occupancy-залежні
  ціни, дитячі ціни, min stay, CTA/CTD, closed periods. Забирається:
  нові брони, зміни, скасування, додаткові послуги (тільки дельти).
- Спека і тестовий доступ — за партнерською угодою з TourOnline.
  **Це найдовший зовнішній lead time — контакт ініціюється першим кроком.**
- **DIRS21 — не джерело істини цін.** Ціни в ньому — ручний зліпок
  прайсу готелю за формулою деривації (у пілота: (стандарт + сніданки)
  × 1,15), і він застаріває, щойно нікому його оновлювати. При
  міграції з DIRS21 забираються лише (а) конфігурація: мапінг
  категорій/room types, канали, min-stay/closeout, політики — для
  адаптера; (б) одноразовий аудит-знімок цін для звірки з задуманим
  прайсом. Самі ціни відбудовуються з прайсу готелю в нашій моделі
  і далі пушаться в канал.
- Перемикання PMS-інтерфейсу об'єкта з одного PMS-партнера на іншого робить
  TourOnline за заявкою готелю (штатний процес зміни PMS).

### 3.1 PriceLabs: динамічні ціни в цільовій схемі

Ціновий потік має рівно одного господаря — нашу PMS:

```
брони/зайнятість (ALiSiO) ──► PriceLabs (Open API, партнерський фід)
PriceLabs ──► рекомендовані ціни ──► price_calendar ──► ARI push у DIRS21 ──► усі канали
```

PriceLabs **не** підключається до DIRS21 чи Winhotel напряму (прямої
інтеграції в них і немає в каталозі): два джерела цін в одному каналі —
гонка записів і овербукінг по тарифах. PMS — єдиний price master.

Поточна реалізація pricelabs-фічі однобока і однокліентна, для нового
клієнта не запрацює:

1. **Хардкод листингів першого клієнта** — `pricing/data/pricelabs-sync.ts`
   тримає мапу listing→unit у коді. Замінюється таблицею
   `pricelabs_listing_map (organization_id, listing_id, unit_type_id)`
   (+ індекс по організації, UNIQUE (organization_id, listing_id));
   перший клієнт мігрується в неї.
2. **Безумовна конвертація EUR→CZK через ČNB** — стає org-aware:
   валюта листинга = валюті організації → без конвертації.
3. **Фід даних у PriceLabs відсутній** — сьогодні цю роль виконує Hostex
   першого клієнта. Для решти світу будуємо outbound-синк за їхнім
   Open API (листинги, календар зайнятості, брони з цінами); доступ —
   за партнерською угодою з PriceLabs, запит іде разом із листом до
   TourOnline (обидва — зовнішні lead time Фази 0).
4. **Зчеплення з §4.10**: PriceLabs дає одну ціну на категорію/дату
   (база = DZ-заселеність) + extra_person_fee; EZ-ціна виводиться
   правилом категорії (офсет/відсоток від бази), сніданок — окремою
   послугою поверх, похідні тарифні плани — на нашому боці.
5. **Мапінг для готелю**: 1 листинг PriceLabs = 1 категорія
   (unit_type), не фізичний номер — і за моделлю, і за тарифікацією
   PriceLabs (оплата за листинг).

Режими впровадження: Фаза 2 — shadow (фід іде, рекомендації видно,
нікуди не пушаться — Winhotel до перемикання лишається господарем цін;
порівняння з ручними цінами = аргумент цінності для готелю); Фаза 3 —
advisory (зміни підтверджує людина); далі — автоматика із запобіжниками:
min/max на категорію, pin ручних цін (ярмаркові дати!), sanity-guard у
синку від абсурдних значень.

Куди це лягає в нас (`src/modules/channels`): generic-каркас уже є —
`channel_connections`, `channel_credentials`, `channel_room_mapping`
(мапінг на `unit_type_id` — правильна модель для DIRS21), `ari_sync_queue`,
`ari_sync_log`. Але інтерфейс `ChannelAdapter`
(`src/modules/channels/domain/types.ts:205`) досі ніким не реалізований:
Booking.com-код — вільні функції, Hostex — узагалі поза абстракцією
(мапінг на `unit_id` у глобальній `hostex_property_map`). DIRS21 робиться
**першою справжньою реалізацією** `ChannelAdapter` + диспетчеризація за
`connection.channel`; `ChannelCode` розширюється значенням `dirs21`.

## 4. Німецькі вимоги (чого системі бракує)

Аудит модулів — 2026-08; файли-докази наведені там, де рішення неочевидне.

1. **ПДВ відсутній як поняття.** Ставок немає ніде; інвойс — один рядок
   однією сумою (`invoices.amount`; `invoice_line_items` не існує;
   `finance/domain/isdoc.ts` захардкожений на `VATApplicable=false` —
   система будувалась під чеського неплатника). Німеччина вимагає
   багаторядковий рахунок §14 UStG з рекапітуляцією за ставками.
   Потрібно: таблиця ставок з датами дії, `vat_rate` на рядку,
   `invoice_line_items`, перепис генератора і шаблону PDF.
2. **Ставки 2026** (звірити зі Steuerberater клієнта перед go-live):
   проживання 7%; з 01.01.2026 їжа в гастрономії 7% — сніданок-їжа 7%,
   **напої 19%**; паушальні розщеплення дозволені (Business-Package: 15%
   пакета під 19%; сніданок: частка напоїв 15–30%). Історичні документи
   до 2026 — за старими правилами (сніданок 19%), тому ставка живе на
   рядку документа, а не глобально.
3. **Meldeschein**: з 01.01.2025 скасований для громадян ФРН, лишається
   обов'язковим для іноземців (папір, власноручний підпис, перевірка
   документа). Наша `guest_registrations`/registry — чеська Evidenční
   kniha; потрібна німецька друкована форма поверх наявних полів
   (`reservation_guests` уже має document_*, nationality, visa_number).
4. **Адмінка тільки українською** (хардкод, без i18n-каркасу) — персоналу
   потрібен німецький інтерфейс. Гостьові поверхні DE вже мають.
5. **CZK-центричність**: дефолти `'CZK'` по схемі й коду, курси лише ČNB,
   формат `cs-CZ` в інвойсі, ISDOC (чеський стандарт). Для DE:
   орг-валюта EUR, формат de-DE, e-Rechnung (ZUGFeRD/XRechnung) — до
   обов'язкового B2B-виставляння 2027/2028, не day-1.
6. **Імпорту немає**: ні гостей, ні номерів, ні історії (єдиний bulk —
   Booking.com Excel, з хардкодами першого клієнта). Потрібен імпортер
   з Firebird: довідники → гості → майбутні брони (+ опційно історія
   для статистики).
7. **DATEV-експорт** для Steuerberater — фаза 2 після go-live.
8. **Kurtaxe**: облік і місячний звіт уже є (`city_tax_*`,
   `reports/city-tax`); бракує лише виводу окремим рядком інвойсу —
   закривається пунктом 1.
9. **Щоденний операційний лист** (Zimmerliste/Frühstücksliste): на
   рецепції день живе на друкованому листі, який заповнюють від руки —
   номер, гість, EZ/DZ-заселеність, сніданок так/ні, гараж (TG),
   оплата готівкою, заїзд/виїзд/залишається, підсумки внизу: скільки
   прибирати, скільки залишається, **скільки сніданків на ранок**.
   Друкований звіт «денний лист» з цих самих даних — перша видима
   персоналу цінність нової системи; робити в числі першого.
10. **Ціни за заселеністю.** У `price_calendar` є лише
   `base_price`/`weekend_price`; occupancy-залежних цін немає ніде
   (аудит: `occupancy_rules` з README модуля pricing не існує, у
   віджеті — лише доплата `extra_person_charge`). Для DE-ринку це
   блокер нарівні з ПДВ: ціна EZ- проти DZ-заселеності — базовий режим
   продажу, і DIRS21 V3 ці ціни передає. Потрібна модель «ціна за
   (категорія, дата, кількість осіб)» + сніданок за особу як послуга.
11. **Договірні корпоративні тарифи** (Firmenraten) — прив'язка
   тарифу до компанії-платника; у нас `rate_plans` без зв'язку з
   компанією. Мінімум day-1: іменований rate_plan на фірму +
   збірний рахунок на Debitor (див. §2). У пілота це окрема сітка цін
   (-10%) + список фірм; частині фірм гараж безкоштовний — тобто
   правило тарифу тягне і ціни послуг.
12. **Авторозщеплення імпортованої OTA-суми** на рядки
   Übernachtung / Frühstück-Speisen / Getränke за правилами організації
   (ціна сніданку, пропорція їжа/напої, OTA-націнка). Розв'язує
   найбільший щоденний біль рецепції пілота і потрібне будь-якому
   німецькому готелю з OTA-каналами. Реалізується разом з §4.1
   (рядки інвойсу) і §4.10 (ціни за заселеністю).
13. **Збір даних гостя до заїзду** (передчекін): у пілота реальний
   кейс неоплати ~700 € через відсутність даних гостя; фірмові брони
   приходять «тільки ім'я». Наш guest portal / реєстрація вже вміє
   більшість — потрібен німецький текст запрошення і зв'язка з
   Meldeschein (§4.3). Депозити готель не бере — ризик закривається
   даними, не передоплатою.

## 5. Фази

**Фаза 0 — доступ і аудит даних.** Копія `winhotel.fdb` (знімається при
закритому Winhotel) + версія Firebird; розбір схеми; лист TourOnline щодо
партнерства V3; запит PriceLabs на партнерський Open API (§3.1); строк
розірвання контракту CDSoft. Вихід: мапа Winhotel-таблиць → наших,
перелік того, що не мігрує.

**Фаза 1 — німецький фундамент.** Порядок: ПДВ+рядки інвойсу (§4.1) →
ціни за заселеністю (§4.10) → DIRS21-адаптер (§3) → імпортер (§4.6) →
німецька адмінка (§4.4) → денний лист (§4.9) → Meldeschein (§4.3) →
Firmenraten (§4.11) → дрібниці.
Інвойс затверджує Steuerberater клієнта на тестових кейсах
(ніч+сніданок+гараж; корпоративний на фірму; іноземець з Meldeschein).

**Фаза 2 — дзеркало.** Організація заводиться `provision-org.mjs`
(валюта EUR, усі фічі off), імпорт структури і брон; далі щоденна дельта
з Firebird (нічний знімок або агент на їхньому Windows). Автозвірка:
зайнятість по днях, суми, податки. Персонал вчиться на дзеркалі.
Критерій виходу: N тижнів звірки без розбіжностей.

**Фаза 3 — перемикання.** Низький сезон, середина тижня. Фінальний імпорт
при замороженому Winhotel → TourOnline перемикає PMS-інтерфейс → повний
ARI-push з нас → ручна звірка доступності в Cockpit21 (захист від
овербукінгу) → персонал працює в нас. Winhotel лишається read-only
архівом у готелі (GoBD: 10 років зберігання — обов'язок готелю, не наш).

**Фаза 4 — пост.** Тиждень щоденної звірки; DATEV; згодом — наш віджет
замість DIRS21 One (опційно), e-Rechnung до 2027.

## 6. Принципи: підключати різні готелі, не роздуваючи продукт

Кожен готель приходить зі своєю ідеологією — електронною (PMS, Excel
довкола неї) і паперовою (денні листи, касові журнали, ключові
відомості). Правила, за якими ми це поглинаємо:

1. **Ядро одне для всіх.** Бронювання, сітка, гості, рахунки, податки —
   спільна модель даних без форків під клієнта. Форк ядра = смерть
   мультитенантності.
2. **Відмінності готелю живуть у даних, не в коді.** Категорії, сезони,
   тарифні правила, послуги, пропорції розщеплення, тексти й шаблони —
   налаштування організації. Тест придатності: нового готелю можна
   завести самим `provision-org` + заповненням довідників, без коміту.
3. **Функції — конструктор.** Реєстр `organization_features` вмикає
   модулі поготельно (сертифікати, зал, паркінг, сауна, передчекін…).
   Відсутній рядок = вимкнено — дефолт мінімальний.
4. **Інтеграції — адаптери за стандартним інтерфейсом.** Channel
   manager (DIRS21, Hostex), платіжка, RMS (PriceLabs) — новий готель є
   новою комбінацією адаптерів, не новим кодом. Хардкоди першого
   клієнта в `hostex-sync`/`pricelabs-sync` — антиприклад, який
   розгрібаємо.
5. **Паперові звички не ламаємо — друкуємо.** У кожного готелю є свої
   папірці; система вміє надрукувати той самий лист, до якого звик
   персонал (денний лист, сніданковий список, касовий журнал). Набір
   друкованих звітів — стандартний, склад полів — конфігурація. Це
   місток довіри при переході, а не легасі.
6. **Правило другого готелю.** Функцію узагальнюємо, коли її просить
   другий готель. Для першого — мінімальна конфігурована версія за
   флагом. Захист від спекулятивної архітектури.
7. **Onboarding — стандартний процес, індивідуальні дані.** Анкета
   готелю (категорії, тарифна логіка, податки, канали, папірці,
   Excel-сателіти) → заведення довідників → дзеркало → перемикання.
   Плейбук один; від готелю до готелю міняється лише вміст.
8. **Жодних імен клієнтів у коді** — `check-no-tenant-names.mjs`
   лишається build-перевіркою; бізнес-словники клієнта живуть у БД.
