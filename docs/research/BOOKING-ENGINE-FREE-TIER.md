# Booking engine: безкоштовний рівень і платіжні стани

**Рішення власника:** `booking_engine` ON віддає движок **і одну хостовану сторінку** на нашому піддомені. `site_builder` OFF гейтить конструктор.
**Доказ:** розбір гостьового застосунку Hoteliera (`guest.hoteliera.com`) — 25 маршрутів, 22 ендпоінти, зняті 31.08.2026. Деталі в `docs/research/`.

> **Стан реалізації на 31.08.2026.** `booking_engine` у реєстрі є (`src/core/features.ts`,
> дефолт ON). Ключа `site_builder` там **немає навмисно**: конструктора в коді ще не
> існує — під сайти є лише `site_listings`, `site_rate_plans`, `site_services` і
> `site_incoming_leads`, тобто дані потоку бронювання, і жодної таблиці сторінок чи
> секцій. Прапорець, який нічого не стереже, — перемикач-обманка в налаштуваннях.
> Він прийде разом зі своєю вартою. Цей документ описує ЦІЛЬ, не поточний стан.

---

## 1. Навіщо

Готель на 1–5 юнітів часто не має сайту взагалі — має сторінку в Instagram. Віддати йому движок бронювання без місця, куди його поставити, означає віддати нічого.

Sirvoy закриває цю діру безкоштовним тарифом: сайт + движок + оплата на одному юніті. Якщо ми віддаємо менше, ми програємо перше враження — а саме воно вирішує в цьому сегменті.

Hoteliera розділила це явно: тип сайту — перелічене поле з двома значеннями.

```
websites.labels: website_type_booking_only · website_type_full
```

`booking_only` — хостована сторінка на їхньому піддомені, яка не має нічого, крім движка. `full` — конструктор із власними сторінками, доменом, секціями.

Беремо цю саму лінію розділу. **Вона вже прокладена в нашій схемі:**
`booking_sites.type CHECK (type IN ('widget', 'self-hosted'))` зі слагом.

## 2. Що входить у `booking_engine` (безкоштовно)

Хостована сторінка на нашому піддомені: `<slug>.alisio.app` або аналог.

**Екрани** (маршрути гостьового застосунку Hoteliera, з яких це знято):

| Екран | Їхній маршрут | Навіщо |
|---|---|---|
| Сторінка об'єкта | `/hotel/:location_id`, `/location/:location_id` | назва, фото, зручності, типи номерів, ціни |
| Пошук і вибір | `/new-reservation` | дати, гості, доступні типи, розклад ціни |
| Оформлення | `/reservation-new` | дані гостя, тарифні умови, купон |
| Підтвердження | `/reservation-confirmed` | номер броні, що далі |
| Пошук своєї броні | `/find-reservation`, `/reservation-search`, `/reservation/:id` | **без акаунта** — гість вводить код і пошту |
| Правові сторінки | `/terms`, `/policies`, `/cancel-policies`, `/order-policies`, `/gdpr-policies` | обов'язкові для ЄС |
| Cookie-згода | модуль `cookie_consent` | GDPR |
| Движок вимкнено | `/ibe-inactive` | окремий екран, не помилка — див. §5 |

**Оформлення:** логотип, шість кольорових токенів, назва об'єкта. Не більше.

> Шість токенів — рівно стільки, скільки треба, і це теж їхнє рішення:
> `background_primary` · `background_secondary` · `background_warning` ·
> `text_primary` · `text_secondary` · `text_footer`.

**Не входить:** власний домен, власні сторінки, секції головної, meta-теги, галерея, спецпропозиції, аналітика.

## 3. Що гейтить `site_builder` (платно)

| Можливість | Їхнє поле |
|---|---|
| Власний домен замість піддомена | `booking_engine_redirect_url`, `client_domain_active`, `redirect_from_subdomain_to_domain` |
| Власні сторінки зі слагами й HTML | `website_pages`: `page_slug`, `content_html`, `menu_name`, типи `page`/`link`/`locked` |
| Секції головної | `homepage_sections`: заголовок + зображення |
| Спецпропозиції | `website_offers` |
| Meta-теги й SEO | `meta_title`, `meta_description`, `meta_keywords`, `favicon_image` |
| Галерея й банер | `homepage_gallery`, `banner_image`, `show_homepage_gallery_slider` |
| Кілька локацій на одному сайті | `assigned_locations`, `homepage_locations_count` |
| Аналітика | `facebook_pixel_id`, `google_analytics_id`, `google_analytics_id_ga4` |
| Тексти «про нас» | `about_us_text`, `discovery_us_text`, `we_offer_excellent_experience_text` |

## 4. Оплата: основний шлях, не крайній випадок

`booking_engine` ON + `online_payments` OFF — це **дефолт для кожного нового готелю**. Отже бронювання без онлайн-оплати не виняток, а типовий сценарій.

**Правило:** оплата — необов'язковий крок за налаштуванням, а не крок, який може зламатися.

### Три стани, які має вміти движок

| Стан | Коли | Що бачить гість |
|---|---|---|
| **Без оплати** | `online_payments` OFF | «Бронювання підтверджено. Оплата при заїзді» + сума й умови |
| **Оплата необов'язкова** | шлюз є, тариф не вимагає передоплати | «Оплатити зараз» або «Оплатити при заїзді» — вибір гостя |
| **Оплата обов'язкова** | тариф вимагає передоплати чи депозит | без оплати бронь не підтверджується, лишається чернеткою |

Третій стан прив'язаний до **тарифного плану**, не до організації: у Hoteliera це `payment_phases` — `on_reservation`, `before_arrival`, `on_arrival`, `deposit`.

### Архітектурна вимога

Створення броні й оплата — **дві окремі операції**, не один крок.

У Hoteliera це видно з ендпоінтів: бронь створюється через `POST /api/reservations`, а оплата йде окремо через `stripe/payment-prep` → редірект → `stripe/payment-status`. Так само `paypal/payment-prep` → `paypal/captured`, `mobilpay/payment-prep`.

Тобто: **бронь існує до оплати і без неї.** Оплата змінює її стан, а не створює.

Це важливо не лише для безкоштовного тарифу. Це також єдиний спосіб коректно обробити відмову шлюзу: бронь уже є, гість повторює оплату, а не бронює вдруге.

### Заглушка, яку можна поставити зараз

Поки жоден шлюз не написаний, `online_payments` OFF, і рух іде першим станом. Це не тимчасовий милиця — це кінцевий вигляд безкоштовного тарифу.

> Уточнення станом на 31.08.2026: у `src/core/payments.ts` **кожен** провайдер має
> `live: false` — код, що говорить зі шлюзом, не написаний узагалі. Тобто перший стан
> сьогодні не «дефолт нового готелю», а єдиний можливий. Тримає `payments.check.ts`.

Писати треба один раз і правильно: **крок оплати рендериться лише коли є налаштований шлюз**, інакше його немає в потоці зовсім. Не «є, але не працює».

## 5. Екран замість помилки

Hoteliera має окремий маршрут `/ibe-inactive` — сторінку «бронювання тимчасово недоступне» замість зламаного екрана чи 404.

Той самий принцип потрібен усюди, де можливість вимкнена прапорцем:

- `booking_engine` OFF → сторінка «бронювання недоступне», з контактами готелю;
- `site_builder` OFF + запит власного домену → редірект на піддомен, не 404;
- шлюз недоступний під час оплати → «спробуйте ще раз або оплатіть при заїзді», з живою бронню.

**Правило:** вимкнена можливість дає пояснення, а не помилку. Помилка — це коли щось зламалось; вимкнено — це стан, і він має свій екран.

> У нас `featureDisabled()` (`src/core/features.ts`) віддає `403` із JSON. Для API це
> правильно; для гостьових СТОРІНОК потрібен екран, а не JSON. Це окрема робота.

## 6. Що це означає для схеми

| Сутність | Зміна |
|---|---|
| сайт | тип `booking_only` / `full`; для `booking_only` домен = наш піддомен, конструктор недоступний. **У нас це вже `booking_sites.type`** |
| `reservation` | стан оплати незалежний від стану броні: бронь може бути підтверджена й неоплачена. **У нас це вже `reservations.payment_status`** — `unpaid \| payment_requested \| prepaid \| partial \| paid` (docs/NAMING.md §2) |
| тарифний план | фаза оплати: `on_reservation` / `before_arrival` / `on_arrival` / `deposit` — визначає, чи обов'язкова передоплата. **Цього в нас немає** |
| платіж | окрема сутність із власним життєвим циклом `prep → redirect → status`, посилається на бронь |

---

## 7. Порядок робіт

1. Тип сайту `booking_only` / `full` + піддомен за замовчуванням для нових організацій.
2. Хостована сторінка: об'єкт → вибір → оформлення → підтвердження.
3. Пошук своєї броні без акаунта.
4. Правові сторінки й cookie-згода.
5. Стан «без оплати» як повноцінний шлях, не заглушка.
6. Екрани вимкнених можливостей.
7. *(після шлюзу)* стани «необов'язкова» і «обов'язкова» оплата за фазою тарифу.

Кроки 1–6 не залежать від платіжного шлюзу й можуть іти паралельно з ядром цін.
