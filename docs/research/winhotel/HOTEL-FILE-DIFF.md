## 3. Ставки ПДВ — історія `STEUSTAM` додана

`apply-hotel.mjs` приймає кілька рядків на код (ключ `code + validFrom`, `validTo`
пишеться), `pickRate()` бере рядок з найпізнішим `valid_from`, що покриває дату
послуги. Тому історія додана, старі рядки лишились:

| Код | Було | Додано з `STEUSTAM` |
|---|---|---|
| reduced | 7 % з 2010-01-01 (без кінця) | 5 % 2020-07-01…2020-12-31; 7 % з 2021-01-01 |
| standard | 19 % з 2007-01-01 (без кінця) | 16 % 2020-07-01…2020-12-31; 19 % з 2021-01-01 |
| zero | 0 % з 2007-01-01 | — (`STEUSTAM` STS 1: 0 % з 2005) |

Для дати в 07–12.2020 переможе 5 %/16 % (пізніший `valid_from`); для 2021+ — рядок
2021 (те саме число, що й відкритий 2010/2007). `STEUSTAM` починає 7 %/19 % з 2005 —
раніше за файл (2010/2007); не змінено: ключ `validFrom` не редагується, а різниця
стосується лише дат до 2010, яких у ALiSiO не буде.

## 5. Серія фактур — рішення власника

| | Було | Стало |
|---|---|---|
| `code` | RE | RE (ключ; не міняється, інакше з'явиться друга серія) |
| `prefix` | `RE` | порожній |
| `numberFormat` | `{prefix}{year}-{seq:4}` → `RE2026-0001` | `{seq}` → `22591` |

Граматика `invoice-number-format.ts`: `{prefix}`, `{year}`, `{yy}`, `{seq}`, `{seq:N}`;
**групування цифр (`22.591`) свідомо не підтримується** — коментар у коді: «чи
продовжує нова система нумерацію попередньої і чи друкує так само — питання до
Steuerberater, не форматна фіча». Тобто на документі буде `22591`, не `22.591`.

**Два кроки поза файлом** (файл цього зробити не може; задача сесії, що володіє
`invoicing`):

1. **Лічильник скидається щороку за побудовою.** `allocateInvoiceNumber` ключує
   `invoice_counters` по `(series, year)` і на 1 січня почне з 1 → `1`, `2`, … замість
   `22592`, `22593`. Колонка `invoice_series.reset_yearly` є (дефолт 1), але аллокатор
   її **не читає**, і `apply-hotel.mjs` її не пише. Потрібно: аллокатор при
   `reset_yearly = 0` ключує по сталому року (наприклад `0`), формат `{seq}` без `{year}`
   — і `apply-hotel` приймає `resetYearly: false`.
2. **Стартовий номер не вигадано.** У день перемикання: `UPDATE invoice_counters SET
   last_no = <MAX(RECHNUNG.RECHNR) з бази того дня>` для серії RE (у знімку 03.2025 —
   `RECHNR` до ~22.5 тис., є ще `RECHNR_ALPHA`; точне число — з `aggregates.txt`
   свіжого знімка, рядок «остання Rechnung-Nr»). Механізму «встановити лічильник» у файлі
   й у скрипті немає — це разова дія на сервері, скриптом (AGENTS §5: немає скрипта —
   спершу створюється скрипт).

## 9. Питання власнику (не блокують деплой файла)

1. **AP 111/112** — у Winhotel їх немає; заводити як номери чи ні.
2. **201 на 1-му поверсі** за базою — одрук чи факт.
3. **Haustier 7 % чи 19 %** — база каже 7 % (рядом із Logis); файл до звірки — 19 %.
4. **Знижка від 3 ночей** — 5,00 на особу (база) чи −10 на номер (файл) при 3–4 особах; чи діє на ES.
5. **Послуги з ціною 0** (Kuchen, Nachlass, Gutschein, Raummiete…) — лишити вимкненими.
6. **Дитячі правила** (Ц30) — потрібні, щоб продавати SD/SK на 4 і DZD/DZK з дитиною.
7. **Komfortzimmer** — у базі немає такої категорії (є `Design`/`Klassik`): якщо на сайті
   чи в прайсі є «Komfort», це або маркетингова назва `Klassik`, або нова категорія після
   03.2025 — уточнити.

## 10. Що потребує коду (не файла) — для контролера

- Аллокатор номерів фактур: `reset_yearly` (§5.1). До цього серія `{seq}` перезапуститься
  1 січня.
- Разовий скрипт «встановити лічильник серії» (§5.2).
- Секція дитячих правил (`extra_occupancy_rules`) у форматі файла й `apply-hotel.mjs`.
