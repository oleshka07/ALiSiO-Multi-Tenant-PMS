# docs/tasks — задачі контролера і правила паралельних кодових сесій

Тут лежать задачі, які контрольна сесія ставить кодовим сесіям. Файл у цій теці — єдине джерело
задачі; вкладення в чат до кодових сесій не доходять. Кожна сесія на старті робить `git pull` і читає
свій файл цілком.

## Гілки

- **Головна гілка робіт:** `claude/channex-integration-66kv65` (= `beta`). На ній працює **сесія 1**
  (ядро цін, канали, оболонка). Бета деплоїться лише з неї, пушем власника.
- **Паралельні сесії** працюють на **власних гілках**, відгалужених від головної:
  сесія 2 — `claude/block-4-hotel-day`, сесія 3 — `claude/block-3-channels` (назви в задачах). У головну і в `main` вона **не пушить**. Раз на день —
  `git fetch origin && git rebase origin/claude/channex-integration-66kv65`, конфлікти вирішує сама
  за правилами нижче. Коли блок готовий і CI зелений — повідомляє власника; злиття в головну робить
  сесія 1 після рецензії контролера (`git merge --no-ff`), не паралельна сесія.

## Що не має перетинатись

Кожна задача називає **теки, які їй належать**, і **теки, яких вона не чіпає**. Правило просте:
файл, названий чужим, не редагується — навіть на один рядок; якщо без цього не обійтись, сесія
пише в звіт «потрібна зміна в чужій теці: файл, рядок, чому» і зупиняється на цьому пункті.

Спільні файли, які чіпають обидві сесії, і як не побитись:

| Файл | Правило |
|---|---|
| `db/postgres/migrations/` | **Діапазони номерів.** Сесія 1: `0068–0089`. Сесія 2 (Блок 4): `0090–0099`. Сесія 3 (Блок 3): `0100–0109`. Порядок накочування — за іменем файла, ledger `schema_migrations` — за іменем, пропуски дозволені (`deploy/migrate.sh`). Номери поза своїм діапазоном не брати |
| `src/lib/db.ts` (SQLite-дзеркало) | свої міграції дописувати **в кінець** блоку міграцій; при rebase конфлікт вирішується збереженням обох блоків у порядку номерів |
| `db/postgres/schema.sql` | не редагується руками (інваріант 10); після rebase — `node scripts/pg-schema.mjs` заново, конфлікт вирішується перегенерацією |
| `docs/DECISIONS.md` | сесія 1 продовжує `Ц…`, `П…`, `Р…`. Сесія 2 пише в **новий розділ «День готелю» з префіксом `Д1, Д2…`** наприкінці файла; сесія 3 продовжує `К4, К5…` у розділі «Канали» — різні місця, git зливає сам |
| `docs/SECURITY-FINDINGS.md` | номери `INC-` роздає лише сесія 1; паралельна записує знахідки в `docs/tasks/<своя задача>.notes.md`, номери отримають при злитті |
| `docs/ARCHITECTURE.md` §8 | кожна сесія — свій підрозділ із назвою блоку; таблиця гейтів — дописувати рядки в кінець |
| `docs/INDEX-FOR-NEW-SESSION.md`, `docs/MASTER-PLAN.md` | лише сесія 1 (контролер). Паралельна не чіпає |
| `src/core/i18n/messages/cs.json`, `de.json`, `catalogue.json` | обидві додають ключі; при конфлікті — взяти обидва набори, потім `npm run check:i18n` |
| `src/components/layout/nav-items.ts` | паралельна додає **лише свої** пункти (Guests → Companies, Housekeeping) окремими рядками в кінці своєї групи |
| `package.json` `"check"` | нові гейти дописувати **в кінець** ланцюжка |

## Чекпоінти вночі

Якщо чекпоінт — рецензія (знімки, форма) або рішення власника, а відповіді немає, сесія **не зупиняється**: залишає цей пункт відкритим, називає його в звіті і йде далі по пунктах, які від нього не залежать. Зупинка лише перед незворотним: міграція живих даних, злиття, запис у вендора.

## Що обовʼязково для всіх

`AGENTS.md` §3 (інваріанти, особливо 21: схема з `origin/beta`), §4 перед комітом. Гейти червоним
першими там, де гроші/броні/документи (інваріант 24, 29). Перед кодом — абзац «що вже є» з
прочитаного. Звіт після кожного коміту, самодостатній: коміти + CI, було→стало з файл:рядок, гейти,
що були червоними, **самостійні рішення окремим списком**, що потрібно від власника.
