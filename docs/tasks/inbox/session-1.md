# Задача 16 — один тип колонки валить `check:pg`, і CI твоєї гілки був червоний, коли ти звітувала

## Дефект — рівно один рядок, і я його знайшов

```
error: invalid input syntax for type bigint: "false"
  at createPaymentMethod (payment-methods.repo.ts:114)
  where: "unnamed portal parameter $7"
```

`$7` — це `settles_to_debtor`. Код пише в неї `true`/`false`
(`payment-methods.repo.ts:121`), а в базі вона **BIGINT**:

```
schema.sql:1023   "settles_to_debtor" BIGINT DEFAULT 0 NOT NULL
migration 0141:63 "settles_to_debtor" BOOLEAN DEFAULT FALSE NOT NULL
```

**Два джерела не сходяться.** Перевірив у трьох базах: `drift_fresh` — `bigint`,
`drift_migrated` — `bigint`, стенд зі `schema.sql` + усі міграції — `bigint`. Тобто виграє
`schema.sql`, а `0141` не міняє тип, бо `CREATE TABLE IF NOT EXISTS` на наявній таблиці мовчить.

**Корінь — у `db.ts`, і він показовий.** Ти оголосила `settles_to_debtor INTEGER`
(`db.ts:6496`), а генератор Postgres-схеми мапить `INTEGER` → `BIGINT`. Сусідній `is_active`
теж `INTEGER` у `db.ts`, але в `schema.sql` він **BOOLEAN** — бо генератор має **іменну
евристику `is_*`**. Твоя колонка під неї не підпадає, і мовчки стала числом. Коментар у самому
писачі («прапорці TRUE/FALSE, не 1/0») каже, що ти мала на увазі саме булеве.

Це той самий клас, який ми ловимо тижнями: **гейт (тут — генератор) вирішує за візерунком імені,
а не за властивістю.** Тому правка не «поміняй тип у db.ts», а:

**1. Полагодь колонку** — так, щоб `db.ts`, `schema.sql` і `0141` казали одне. Обери й напиши
чому: булеве в обох (тоді генератор мусить дізнатись про це не з імені) або число в обох (тоді
писач пише `1/0`, а коментар про TRUE/FALSE знімається).

**2. Полагодь ЕВРИСТИКУ, а не свою колонку.** Іменна мапа `is_*` — це рівно «зелено, бо гейт
рахує візерунок». Наступний `settles_*`, `has_*`, `allows_*` мовчки стане числом так само.
Виміряй спершу: **скільки колонок у `db.ts` оголошені `INTEGER` і використовуються як прапорці**
(пишуться `true/false` або порівнюються з булевим). Число в звіт — воно вирішує, чи це одна
колонка, чи клас.

**3. Гейт на властивість.** `check-schema-drift` цього не спіймав і не міг: обидві його бази
будуються так, що `schema.sql` іде першим, тож розбіжність «схема проти міграції» ховається.
Властивість, яку треба стерегти: **тип колонки в міграції збігається з типом у `schema.sql`**.
Червоний до правки — на твоїй же `0141`.

## І головне — процес, а не код

**CI твоєї гілки був ЧЕРВОНИЙ, коли ти звітувала.** Прогони `checks` #874 (`7b6a2163`) і #878
(`d9c3677e`) — обидва `failure`, обидва на завданні `queue and transaction checks on the pool`,
обидва з цією ж помилкою. Сигнал був, і він був твій власний.

Через це червоне поїхало в гілку робіт, звідти на бету, і **прод стоїть уже другу годину** —
не через складність, а тому що ніхто не подивився на прогін своєї гілки.

Тому правило, дописане в `AUTOLOOP.md` цим же комітом: **задача не закінчена, поки `checks` на
твоїй гілці не зелений.** Не «я прогнала локально» — локально `npm run check` бігає на SQLite,
де `false` у числову колонку лягає без слова, і саме тому воно зелене в тебе і червоне в CI.
Це той самий інваріант, який ти сама застосовувала до інших: **роль і середовище вимірювання є
частиною вимірювання.**

Якщо CI недоступний або довгий — скажи це в звіті прямо («CI не дочекалась, ось чому»), і я
дочекаюсь замість тебе. Мовчазне «готово» при червоному прогоні — єдине, чого робити не можна.
