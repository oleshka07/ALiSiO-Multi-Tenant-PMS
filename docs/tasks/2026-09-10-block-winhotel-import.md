## 1. Рішення, які вже ухвалені (не перепитувати)

- Доставка: **агент на сервері готелю** робить знімок і завантажує; **міст** у нас відновлює
  й витягає; **застосунок** імпортує. Жодного читання живої бази з мережі.
- CDSoft не в ланцюжку; пароль SYSDBA — не умова (§2.1: три режими знімка).
- Знімок — файл `.fbk` (gbak) або, у запасному режимі, копія `.fdb`. Обидва відновлюються
  `gbak -c` у Firebird 3 (перевірено 10.09 на справжніх 407 МБ).
- Образ застосунку (`Dockerfile`) **не змінюється**: Firebird живе лише в окремому контейнері
  `bridge`. Він не має доступу до Postgres і не має мережі назовні.
- Таблиці застосунку — свої (`winhotel_*`), з `organization_id` і RLS; **у таблиці ядра
  нових колонок не додаємо**. Відповідність «рядок Winhotel → наш рядок» живе в
  `winhotel_refs`, не в ядрі.
- Що ядро зараз не вміє (Sammelrechnung/дебітор, фірмовий тариф ↔ компанія, 24 способи оплати,
  згоди GDPR на гостя — `CORE-GAPS.md`) — **не імітувати в застосунку**. Дані кладуться в
  `winhotel_staging` як JSON, з назвою сутності й лічильником у звіті імпорту; коли ядро
  навчиться — окрема задача перенесе їх зі staging. Втрата даних неприпустима, підробка ядра
  — теж.
- Історичні фактури Winhotel (33 059) імпортуються **заморожені**, не перераховуються
  (`00-JOURNAL` §4.3; інваріант 18): якщо фасад `@invoicing` не має дверей для
  «фактура-знімок із чужою нумерацією й чужим TSE», вони лягають у `winhotel_staging`
  (`entity = 'invoice'`) з повним JSON і **звіт це називає числом**; двері у фасад — задача
  сесії 1, не ця.
- Готель у ALiSiO уже заведений (`hotels/schlossberghotel.json`, `apply-hotel`); імпорт **не
  створює** категорії, номери, послуги, ставки — він їх **знаходить** за кодом/назвою і
  відмовляє з переліком, якщо чогось немає (інваріант 17: вигаданого не існує).
- Мова екрана — через каталог (`check:i18n`), як в усьому блоці застосунків.

## 2. Обсяг — усе в одній гілці, у такому порядку

### 2.1 Агент на сервері готелю — `apps/winhotel-agent/` (не в `src/**`)

Один файл PowerShell `winhotel-agent.ps1` + `README.de.md` (для того, хто ставить на місці)
+ `install.ps1`, який реєструє завдання планувальника Windows на 03:00. Агент:

1. знаходить Firebird (`gbak.exe` у `C:\Program Files\Firebird\Firebird_3_0\`, або з
   реєстру, або поруч із Winhotel) і базу (`c:\winhotelmx\daten\winhotel.fdb`; шлях — параметр);
2. обирає **режим знімка**, у такому порядку, і пише в лог, який спрацював:
   **(а)** готовий `.fbk` із теки бекапів Winhotel (параметр `-BackupDir`; беремо
   найсвіжіший, якщо він молодший за 24 год) — коли готель уже робить бекап сам;
   **(б)** `gbak -b` з паролем: шукає `SYSDBA.password` у теці Firebird, потім
   `-Password` з параметрів, потім `masterkey`; кожну спробу логує без пароля;
   **(в)** копія файла `winhotel.fdb` (лише якщо Winhotel закритий: перевірка, що файл
   відкривається на запис ексклюзивно; інакше — відмова з текстом);
3. стискає (`.gz`), рахує sha256, шле `POST {ALISIO_URL}/api/apps/winhotel-import/snapshots`
   з заголовком `Authorization: Bearer <токен застосунку>` і полями `sha256`, `mode`,
   `takenAt`, `hostname`; повтор 3 рази з паузою; відповідь `201 {snapshotId}` — успіх, будь-що
   інше — у лог і код виходу ≠ 0 (щоб планувальник показав червоне);
4. чистить свої тимчасові файли; нічого в теці Winhotel не змінює й не видаляє.

Токен агента: генерується на картці застосунку (§2.4), зберігається в
сховищі ключів застосунків (`src/core/integration-credentials.ts`, таблиця `channel_credentials`) під `winhotel_import` — як ключі fiskaly/smtp, не новою таблицею, показується
один раз. У скрипті — з параметра або з файла `agent.token` поруч (README каже, що файл
читається лише адміністратором).

### 2.2 Прийом знімка — `src/app/api/apps/winhotel-import/snapshots/route.ts`

- `POST` без сесії: **публічний маршрут, право — токеном** (інваріант 4; запис у
  `src/proxy.ts` з причиною; `check-route-guards`, `public-tenant`, `check-public-routes`
  мають лишитись зеленими). Токен → організація; немає/чужий → 401, застосунок вимкнений
  для організації → 404 (не 403, інваріант 5). Тіло — потік у файл на томі
  `winhotel-snapshots` (`/app/data/winhotel/<org>/<snapshotId>.fbk.gz`), **не в памʼять**;
  sha256 звіряється з заголовком, розбіжність → 400 і файл видаляється.
- Рядок у `winhotel_snapshots` (міграція **0143**): `id, organization_id, taken_at, mode,
  sha256, size_bytes, status ('received'|'extracting'|'extracted'|'imported'|'failed'),
  error, counts_json, received_at, imported_at`. Ліміт: один знімок на добу на організацію
  (повтор того самого sha256 → 200 з тим самим id, без другого рядка).
- `nginx`: `client_max_body_size` для цього шляху — 200m (`deploy/nginx/alisio.conf`, окремий
  `location`), решта лишається 25m. Це deploy-файл — правка мінімальна, у звіті названа.
- `reportOk('winhotel_import', org)` після прийому; `reportError` з текстом на кожній відмові
  (не `e.message`, інваріант 6).

### 2.3 Міст — `deploy/bridge/` (окремий контейнер)

- `deploy/bridge/Dockerfile`: `debian:bookworm-slim` + `firebird3.0-utils` + `node:22`
  (або `firebird3.0-server` у embedded-режимі — так робив `extract.sh`); `deploy/docker-compose.yml`:
  сервіс `bridge` під `profiles: ["bridge"]`, без портів назовні, спільний том
  `winhotel-snapshots` з `app`, `mem_limit` (відновлення 400 МБ бази бере ~1 ГБ на диску й
  ~300 МБ RAM — виміряти й записати), `read_only` де можливо. `deploy.sh` його не збирає без
  профілю — це свідомо: у готелів без Winhotel міст не запускається.
- Протокол: міст **дивиться на том** (без HTTP): файл `<id>.fbk.gz` + маркер `<id>.ready`
  → відновлює `gbak -c` у `/tmp/<id>/db.fdb` → ганяє **набір SQL** з
  `apps/winhotel-import/sql/*.sql` (один файл на сутність за `IMPORT-PLAN.md` §1–2, кожен
  із `TA_STATUS < 1000`, `isql -q -charset NONE`, вихід у JSON-рядки через `SELECT … FROM …`
  з розділювачем, або через `node-firebird`? — **обери один спосіб і назви чому**) →
  пише `<id>/<entity>.jsonl` + `<id>/aggregates.json` (числа з `COUNTS-2025-03.md` §2 і
  кроку 7 `extract.sh`) + `<id>.extracted` → **видаляє відновлену базу**. Помилка →
  `<id>.failed` з текстом. Застосунок читає маркери й переводить статус рядка.
- Перекодування CP1252 → UTF-8 і суми `/1000` — у мосту, один раз, щоб застосунок бачив
  уже нормальні дані; дати `1899-12-30` → `null` там само.
- Міст **ніколи** не читає Postgres і не має `DATABASE_URL`.

### 2.4 Картка застосунку — екран «Застосунки» (уже є) + сторінка застосунку

На картці `winhotel_import` (`live: true` після цієї задачі): стан звʼязку (останній знімок:
дата знімка `taken_at`, режим, розмір, статус), кнопка **«Токен агента»** (створити/замінити,

знімок»** (для `extracted`), таблиця останніх 10 знімків із числами звірки (§2.6) і журнал
відмов. Усе під `withOwner`; чужа організація нічого не бачить (RLS на `winhotel_*`).

### 2.5 Імпорт у ядро — `src/apps/winhotel-import/` (або де живуть застосунки за
`docs/ARCHITECTURE.md`; **не всередині модулів**)

Порядок і правила — `IMPORT-PLAN.md` §1–2 дослівно, у такому обсязі:

1. **Довідники — лише звірка**: категорії (`KATESTAM.KATEGORIE` ↔ `unit_types.code`), номери
   (`ZINR` ↔ `units.code`), послуги (`LEISTSTA.BEZEICHN` ↔ `additional_services.name`), ставки
   (`STS` ↔ `fin_tax_rates.code`). Розбіжність → імпорт **не починається**, відповідь називає
   кожен незнайдений код. Нічого не створюється.
2. **Гості й компанії** з `ADRESSEN` (`DEBI_NR` → компанія; інакше гість): через фасади
   `@guests` / `@companies`; ключ злиття `SUCHNAME+PLZ+GEBDAT` за планом; `winhotel_refs`
   (`organization_id, entity, winhotel_lnr, our_id, UNIQUE(organization_id, entity, winhotel_lnr)`)
   — і **тільки через нього** повторний імпорт знаходить свій рядок. Персональні дані —
   у базі орендаря, ніде більше (ні в логах, ні в `counts_json`).
3. **Брони** з `GASTKONT` (+ `BELEGUNG` для номера/дат) → `reservations` через `@bookings`;
   стан за мапою з плану (гіпотезу `BUCH_STATUS`/`CI_STATUS` перевірити на агрегатах
   першого знімка й записати в `notes.md`); три адреси → `reservation_guests`; `VERK_NR` →
   група; майбутні брони (заїзд після дати знімка) — **обовʼязково всі**, минулі — за
   параметром «з дати» (дефолт 01.01.2025), решта — лічильник у звіті.
4. **Рядки рахунків** `BUCHKONT` → `fin_folio_items` через `@invoicing` (фоліо = бронь);
   суми як є (не перераховувати), ПДВ-код за `STS`.
5. **Оплати** `ZAHLUNGEN` → `fin_folio_payments` (`DEVISEN` → наші чотири класи; решта
   способів — у staging із лічильником).
6. **Фактури** `RECHNUNG` (+`RECHNUNGSDRUCK`) — заморожені, див. §1: через фасад, якщо є
   двері; інакше `winhotel_staging(entity='invoice')`.
7. **Сальдо** (§3 плану): відкриті дебіторські, депозити, ваучери як послуги — у staging із
   сумами; у ядро — лише те, для чого є сутність (`gift_cards` для ваучерів, якщо ключ і сума
   відомі).
8. **Ідемпотентність**: той самий знімок двічі → нуль нових рядків у ядрі й у refs (гейт);
   новіший знімок → оновлює лише те, що змінилось (порівняння за полями, не сліпий UPDATE);
   видалене у Winhotel (`TA_STATUS ≥ 1000` для рядка, який ми вже імпортували) → у нас
   скасування/архів через фасад, ніколи `DELETE`.
9. Усе в одній транзакції на сутність, під `runWithOrganization`; писачі — через фасади
   модулів (`check-boundaries` зі стелею **як є**: нові пробої не допускаються; якщо
   фасаду бракує дверей — staging + звіт, не пробій).

### 2.6 Звірка після імпорту

`counts_json` знімка: для кожної сутності — у Winhotel (з `aggregates.json`), імпортовано,
оновлено, у staging, пропущено з причиною. Плюс §5 плану: 15 чисел, які мусять зійтись один
в один (номери, категорії, майбутні брони, гості з майбутніми бронями, відкриті фактури…),
і числа з поясненою різницею. Розбіжність у «мусять зійтись» → статус знімка
`imported` із прапорцем `mismatch` і червоним рядком на картці — не тихо.

### 2.7 Гейти — червоним першими, процитувати

`src/apps/winhotel-import/winhotel-import.check.ts` (підключити в `check` і `check:pg`),
фікстура — **дві організації**, невироджені осі (інваріант 26): знімок без токена → 401;
токен чужої організації → 404; sha256 не збігається → 400 і файла немає; той самий знімок
двічі → один рядок і нуль нових записів у ядрі; `TA_STATUS ≥ 1000` не імпортується;
`1899-12-30` → NULL; `141000` → `141.00`; `ÜF` у CP1252 → правильний UTF-8; незнайдений код
категорії → імпорт не починається і називає код; майбутня бронь із трьома адресами → три
`reservation_guests`; повторний імпорт з оновленою датою виїзду → одна бронь, нова дата;
Sammelrechnung-фактура → staging, не ядро, і лічильник у `counts_json`; гість чужої
організації не видимий через refs. Стаб мосту — `<id>/*.jsonl` з фікстури, справжній міст у
гейті не запускається (він — §2.8).

## 3. Чого не робити

- Не читати живу базу готелю з мережі; не писати в теку Winhotel; агент нічого не видаляє.
- Не додавати колонки в таблиці ядра; не робити `DELETE` у ядрі; не перераховувати фактури.
- Не імітувати в застосунку те, чого ядро не вміє (`CORE-GAPS.md`) — staging + звіт.
- Не змінювати `Dockerfile` застосунку, `checks.yml`, стелі гейтів, чужі теки.
- Персональні дані — лише в базі орендаря: не в логах, не в `counts_json`, не в git (гейт
  `check-no-tenant-names` + PII-grep README дослідження).
- Жодних секретів у репозиторії; токен агента — хеш у базі, значення показується раз.
