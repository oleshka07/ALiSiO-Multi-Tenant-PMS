# Обмеження на тарифі (Ц32 переглянуто) — сесія 1, перед кроком 4 Блоку 2

**Від:** контрольна сесія, 07.09.2026. **Ухвалив:** власник 07.09 (скасовує рішення 15а / Ц32
«обмеження лишаються на типі»). **Гілка:** головна. **Пріоритет:** вище за крок 4 Блоку 2 — це
блокер перегравання Channex.

## Чому

Тести 5, 7, 8 сертифікації ставлять **різні** обмеження на різні тарифи одного типу (5: Twin BAR
23.11 = 3, Double BAR 25.11 = 2, Double B&B 15.11 = 5; 7: Twin BAR 01–10 CTA/max 4/min 1, Twin B&B
12–16 CTD/min 6; 8: Double BAR min 3, Double B&B не чіпати) і перевіряють тіло по тарифах. З
обмеженнями на типі кожен тариф типу отримує чуже — «Unexpected rate plan in update», «covers …,
expected …». Декларація у формі минулого разу не допомогла. І продуктово: Hoteliera тримає min/max
stay на тарифі (`org-settings-financials-rate-plans-0`: «Customize min/max stay per room type» —
усередині тарифу), Channex — на тарифі за означенням.

## Модель

Рядок `price_calendar` з `rate_plan_id` (пара) може нести обмеження (`min_stay, max_stay, closed,
cta, ctd`) — колонки вже є. **Ефективне обмеження пари = значення на рядку пари, якщо воно задане,
інакше базовий рядок типу.** «Задане» — `NOT NULL`: для цього колонки обмежень на рядку пари стають
nullable (міграція 0071; на базовому рядку дефолти лишаються). «Закрито» так само: пара може бути
закрита при відкритому типі; тип закритий → усі пари закриті (И14, липкість лишається).

Писачі (`price-calendar.repo.ts`):
- `upsertPrices`/`bulkUpdatePrices` **з `ratePlanId`** — обмеження в рядок пари (не в базовий, як
  зробив A1); маска обмежень рахується проти ефективного обмеження пари; координата — лише ця пара.
- **без `ratePlanId`** («усі тарифи типу» — прапорець у редакторі дня і масовому редакторі, дефолт
  увімкнений, підпис «на всі тарифи типу») — базовий рядок; координати — всі пари типу; рядки пар зі
  своїми значеннями **не затираються** (як `keepManual` для ціни) — це ж значення показуються в сітці
  з позначкою «власне».
- Скинути власне обмеження пари → NULL (успадкувати від типу) — окрема дія/значення «як у типу».

Читачі: `dayRestrictions`/`restrictionsAt` приймають пару і повертають ефективне; `priceNights` для
котирування тарифу читає ефективне обмеження **пари**; `ari-batch`/`ari-adapter` — обмеження пари, не
типу; звірка `verify` — читає назад по опціях і порівнює з ефективним пари; повний синк — дефолти
лише коли ні пара, ні тип не мають значення. Сезони/похідні обмежень не пишуть (крок 1 — не змінюється).

## Гейти (червоним першими)

1. `price-calendar.repo.check`: дві пари одного типу, мінімум 3 лише на BAR → котирування B&B бачить
   1 (базовий), BAR — 3; «на всі тарифи» → обидві 2, власне значення BAR лишилось 3.
2. `ari-adapter.check`: тест 5 дослівно — три пари, три дати, три мінімуми, три координати, тіло без
   зайвих тарифів; тест 7 — два діапазони на двох тарифах Twin, кожен лише свій; тест 8 — мінімум лише
   на Double BAR, Double B&B у тілі немає.
3. `verify-adapter.check`: розбіжність на рівні пари не «лагодиться» значенням типу.
4. `nightly-price.check`: закрита пара при відкритому типі → `missing` лише для цієї пари.
5. `check-fixture-axes`: осі «обмеження на парі / на типі», «пара закрита / тип закритий».
