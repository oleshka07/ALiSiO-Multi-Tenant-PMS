### Що зроблено — було → стало

**1. Тип області — `src/core/property-scope.ts` (новий).**

```ts
type PropertyScope = { kind: 'one'; id: string } | { kind: 'all' }
```

- `propertyScopeFilter(scope, alias)` → `{ sql, params }`. Для `'all'` це
  `TRUE`, а не порожній рядок: порожній треба вміти приклеїти («AND» перед
  нічим — синтаксична помилка), і кожен виклик винаходив би склеювання
  по-своєму.
- `requirePropertyScope(raw)` — двері з запиту, симетрично до
  `requirePropertyId()` (`src/core/auth/tenant-context.ts:135`) для писачів:
  `all` словом → усі; свій id → він; чужий → 404 (інваріант 5); з одним
  обʼєктом мовчання → той обʼєкт; з кількома мовчання → 400. Саме тут раніше
  стояло мовчазне «всі» (інваріанти 8 і 13).
- `ALL_PROPERTIES`, `oneProperty(id)`, `scopedPropertyId(scope)`.

**2. Спільна фікстура — `src/core/fixtures/two-properties.ts` (новий).**

Одна організація, ДВА обʼєкти. Числа підібрані під другу половину інваріанта

|---|---|---|---|
| номерів | **5** (типи 3 + 2) | **7** | **12** — не 5 і не 7 |
| типів номерів | 2 | 1 | 3 |

### Інвентар — звірка з числами контролера

Задача просила перевірити числа власним способом і сказати, де вони
розійшлися. **Таблиці сходяться точно, читання — ні.**

| | контролер (`05af394`) | ця сесія (`9bf24abd`) |
|---|---|---|
| таблиць усього | 121 | **121** |
| з `organization_id` | 79 | **79** |
| з `property_id` | 33 | **33** |
| мовчазних читань | 258 у 91 файлі | **399 у 130 файлах** |

Різницю виміряв, а не оцінив: прогнав СВОЄ сканування ще раз, лишивши все
однаковим і помінявши тільки те, що означає «називає обʼєкт».

| тест «називає обʼєкт» | мовчазних | файлів |
|---|---|---|
| слово `property_id` трапилось у запиті (як у контролера) | **264** | **98** |
| запит ОБМЕЖЕНО по обʼєкту (як у гейта) | **399** | **130** |

Тобто **264 проти 258 у контролера, 98 файлів проти 91** — на різних комітах
(`9bf24abd` проти `05af394`) це той самий вимір; сканування збігаються.
**Уся розбіжність 399 − 264 = 135 запитів — це запити, які НАЗИВАЮТЬ обʼєкт,
не обмежуючи по ньому.** `SELECT property_id FROM units WHERE id = ?` називає
обʼєкт у переліку колонок і не обмежує по ньому нічого; `JOIN properties p ON
p.id = u.property_id AND p.organization_id = ?` — це вісь орендаря.

Дві менші відмінності, обидві навмисні і обидві в бік суворішого:

1. **`JOIN` рахується.** Контролер шукав `FROM <таблиця>`; читання
   `… FROM reservations r JOIN units u …` — це читання і `units` теж.
2. **Одиниця — ЗАПИТ, а не пара «запит × таблиця».** Джойн на три
   scoped-таблиці — одне місце, не три: у храповику виправляється запит, а не
   таблиця в ньому. (Тим самим лічильником по парах те саме дерево дало б
   335 у 98 файлах — число, яке нікуди далі не йде, наведене для повноти.)

**Сигнал контролера підтверджується і трохи розширюється.** Таблиці з НУЛЕМ
названих читань: `gift_cards`, `event_bookings`, `event_spaces`,
`partner_reports` — і до них додається **`event_addons`** (0 названих / 2
мовчазних).

### Знахідка, якої не було в задачі — і вона важлива для сесій 1 і 2

**У девʼяти з 33 таблиць `property_id` NULLABLE:**

```
channel_rate_rules  fin_fiscal_outages  fin_folio_payments  fin_folios
partner_reports     price_los_tiers     price_occupancy     task_projects  tasks
```

Переведення такого читача на `{ kind: 'one' }` **тихо ховає рядки з NULL** —
рівно той самий звір, що рядок без орендаря (інваріант 12): рядок є, його не
видно, у логах нічого. Це б'є переважно по теках **сесії 1**
(`fin_folios`, `fin_folio_payments`, `partner_reports`) і **сесії 2**
(`channel_rate_rules`, `price_*`).

Тому переведення такого читача починається не з фільтра, а з відповіді на
питання «що означає NULL у цій таблиці»: засипати міграцією чи назвати
«спільний для рахунку» і читати `(… = ? OR … IS NULL)` свідомо. Записано в
`ARCHITECTURE.md §4.3.1` і в шапці `propertyScopeFilter`.

### Самостійні рішення (окремим списком)

1. **Розширив наявний гейт другою віссю замість нового файла.**
   `check-property-scope.mjs` уже існував і вже стояв у `npm run check` —
   стеріг інтерфейс. Дві половини однієї вади в одному місці; новий гейт
   `check-property-reads` довелось би пояснювати щоразу поруч зі старим.
   Записано в ARCHITECTURE §7 (рядок гейта).

2. **Базлайн — окремий файл `scripts/property-scope-baseline.json`, а не мапа
   всередині гейта** (Ц/О10 у DECISIONS). `audit-by-id-scope` і
   `check-boundaries` тримають стелі в тілі гейта — для одного автора це
   правильно. Тут авторів три, і `docs/tasks/README.md` забороняє редагувати
   чужий файл. Дані окремо від коду: сесії 1 і 2 опускають свої рядки в JSON,
   гейт лишається за сесією 3, git зливає рядки сам.

3. **Ціни в фікстурі — не з цінових таблиць.** Задача просила «свої ціни» в
   кожного обʼєкта, і перша редакція сіяла `price_occupancy`. Це завалило
   `check-price-source --strict` (інваріант 16: цінові таблиці питає лише
   `modules/pricing`), і гейт має рацію — «додати виняток» тут означало б
   рівно те, від чого він захищає. Грошова вісь узята колонками, які цінових
   таблиць не заміняють: `unit_types.extra_person_charge` (300/450 проти 900)
   і `reservations.total_price` (1000 проти 3300). Перевірці, якій потрібні
   саме нічні ціни, їх досіває СВІЙ модуль через `@pricing` поверх цієї
   фікстури.

4. **Імʼя `PropertyScope` тепер має три значення, і я його не перейменовував.**
   `src/ui/PropertyScopeContext.tsx:51` уже експортує тип із такою назвою —
   це значення React-контексту (`properties[]`, `propertyId`, `setPropertyId`,
   `refresh`), тобто зовсім інша річ. Файл не в моїх теках, тож правку не
   робив; правильним було б `PropertyScopeValue`. Записано в NAMING §8
   рядком «property scope» разом із причиною. **Це не заважає компіляції** —
   модулі різні, імпорти різні.

5. **Три спільні файли зачеплені, кожен мінімально:**
   - `package.json` `"check"` — новий рядок дописаний **у кінець** ланцюжка
     (правило `docs/tasks/README.md`);
   - `scripts/check-fixture-axes.mjs` — 6 рядків реєстру **в кінець** масиву;
     це вимога інваріанта 26, а не вибір;
   - `scripts/check-outbox-writers.mjs` — один рядок `ALLOWED` із причиною:
     фікстура сіє в тимчасову базу, у якої немає жодного каналу; координата в
     черзі там була б неправдою.
   - `docs/ARCHITECTURE.md` — рядок гейта `check-property-scope` **переписано**
     (він мій), поруч дописано рядок `property-scope.check.ts`; §4.3 дістав
     підрозділ §4.3.1; §8 — свій пункт. Правило README «дописувати в кінець»
     стосується §8 і таблиці гейтів; рядок свого гейта редагував свідомо.

6. **`requirePropertyScope` строгий від народження.** З кількома обʼєктами і
   без параметра — 400, а не «усі». Це можна було зробити мʼяко, але тоді
   мовчазний дефолт просто переїхав би в нове місце. Ризику зламати екрани
   немає: функція нова, викликачів у неї сьогодні нуль — вони зʼявляються
   свідомо, у комітах переведення.

### Що потрібно від власника

Нічого для цього коміту. Одне рішення знадобиться далі й краще, щоб воно
дозріло: **що означає NULL у `property_id` девʼяти таблиць** (список вище) —
«ще не привʼязано» чи «спільне для рахунку». Від відповіді залежить, чи
переведення цих читачів супроводжується міграцією-засипкою, чи читанням
`(… = ? OR … IS NULL)`. Питання не термінове: до цих таблиць доходять сесії 1
і 2, і кожна може почати з тих читачів, де колонка `NOT NULL`.
