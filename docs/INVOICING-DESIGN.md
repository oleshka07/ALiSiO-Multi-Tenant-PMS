# Фактурний модуль: фоліо, рядки, ПДВ, нумерація

Дизайн до реалізації. Мотивація — німецький ринок ([WINHOTEL-DIRS21-MIGRATION.md](WINHOTEL-DIRS21-MIGRATION.md) §4.1),
але модель загальна: чеський платник ПДВ ляже в неї ж. Після реалізації
розділ моделі даних переноситься в ARCHITECTURE.md, цей файл лишається
записом рішень «чому так».

Поточний стан (аудит 2026-08): `invoices` — один рядок, одна сума, нуль
ПДВ; `reservation_line_items` живе окремо і в фінанси не потрапляє;
ISDOC захардкожений під неплатника. Це не розширюється правками —
потрібна нова основа.

---

## 1. Ключове рішення: фоліо ≠ фактура

**Фоліо** — накопичувач нарахувань броні під час проживання (жива
робоча сутність). **Фактура** — юридичний незмінний знімок частини
фоліо на момент виставлення. Це розв'язує одразу:

- нарахування протягом проживання (бар, гараж, сніданки) без «переробки
  рахунку»;
- рахунок посеред проживання (гість платить при заїзді — реальний кейс
  пілота);
- розщеплення платників: **кілька фоліо на одну броню** (фірма платить
  ночівлі, гість — бар; у пілота це щоденна практика);
- збірний рахунок фірмі за місяць (Sammelrechnung) — фактура з фоліо
  кількох брон одного дебітора;
- коректність корекцій: фактура не редагується і не видаляється —
  тільки сторнується (у Winhotel видалення рахунку «підвішує програму»
  і з'їдає пів дня — сюди не повертаємось).

## 2. Таблиці

Префікс `fin_` (NAMING §2). Усі таблиці — з `organization_id` та
індексом по ньому. PK — TEXT randomblob-дефолт.

### fin_tax_rates — довідник ставок ПДВ з датами дії

| колонка | тип | примітка |
|---|---|---|
| organization_id | TEXT FK | |
| code | TEXT | `standard` \| `reduced` \| `zero` — закритий словник |
| rate | NUMERIC(5,2) | 19.00, 7.00, 0.00 |
| valid_from, valid_to | DATE | ставка обирається за **датою послуги**, не датою фактури: сніданок 12.2025 = 19%, 01.2026 = 7% |
| label | TEXT | текст для рекапітуляції |

Ставка на рядку зберігається **значенням** (snapshot), довідник — лише
для вибору чинної. Джерела ставок: `additional_services.vat_code`,
`fees_taxes.vat_code`, ставка проживання — налаштування організації
(нові колонки; словник код→чинна ставка резолвиться на момент
нарахування).

### fin_folios — рахунки-накопичувачі

| колонка | примітка |
|---|---|
| organization_id, reservation_id | у Sammelrechnung фоліо різних брон зводяться на фактурі, не тут |
| payer_kind | `guest` \| `company` |
| guest_id / company_* snapshot | назва, адреса, USt-IdNr, debtor_no — копія полів, не FK на живий довідник |
| status | `open` \| `settled` |

Дефолт: одне фоліо на броню, payer з броні. Друге створюється явно
(«перенести позиції на фірму»).

### fin_folio_items — нарахування

| колонка | примітка |
|---|---|
| folio_id, reservation_id, organization_id | reservation_id лишається і на рядку — для Sammelrechnung і звітів |
| service_date | DATE, **Leistungsdatum** — визначає ставку і потрапляння в день-звіти |
| kind | `lodging` \| `service` \| `fee` \| `city_tax` \| `manual` |
| description | текст рядка як піде у фактуру |
| quantity, unit_price_gross | ціни **брутто** — так мислить готель і так приходить з OTA |
| vat_rate | NUMERIC(5,2), значення-snapshot |
| total_gross | `money(quantity × unit_price_gross)` |
| source | `nightly` \| `ota_split` \| `manual` \| `restaurant` \| `import` |
| voided_by_item_id | сторно-рядок замість DELETE після виставлення фактури |
| invoice_id | NULL поки не виставлено; фактура «забирає» рядки |

Джерела наповнення:

1. **lodging** — матеріалізація ночей з ціни броні (за заселеністю);
2. **ota_split** — автррозподіл імпортованої суми: `lodging = сума −
   осіб × ціна_сніданку`; сніданок → два рядки Speisen/Getränke за
   пропорцією організації (у пілота 12+3). Правила — в налаштуваннях
   організації, не в коді;
3. **послуги/збори** — з `additional_services`/`fees_taxes` з їхніми
   ставками; Kurtaxe — рядок `city_tax` зі ставкою 0/7/19 за
   конфігурацією;
4. **manual/restaurant** — рецепція дописує бар/ресторан руками
   (POS-інтеграція — не day-1).

### Нумерація — ВЖЕ Є: `invoice_counters` + `invoice_periods`

Станом на 2026-08 у коді вже існують `invoice_counters
(organization_id, series, year, last_no)` і `invoice_periods
(organization_id, series, month, open|locked)` з модулем
`finance/invoice-numbering` — дизайн **спирається на них**, нову
таблицю послідовностей не заводимо. Додається зверху: формат номера
шаблоном організації, правило «сторно отримує наступний номер тієї ж
серії, оригінал свій номер зберігає назавжди», і заборона виставлення
у закритий (locked) місяць.

### invoices — розширення наявної таблиці

Додається: `number` (UNIQUE per org), `series`, `issue_date`,
`service_from`, `service_to`, `seller_*` snapshot (назва, адреса,
Steuernummer/USt-IdNr — з організації на момент виставлення),
`status` (`issued` \| `storno` \| `corrected`), `corrects_invoice_id`
(self-FK: сторно → оригінал), `locale`, `is_small_amount` (див. §3).
Наявні `custom_buyer_*` стають снапшотом покупця. Поле `amount`
лишається як брутто-підсумок (сумісність).

### fin_invoice_lines — незмінний знімок рядків

Копія полів folio_items на момент виставлення + `position`,
`net_amount`, `tax_amount` (обчислені). Жодних FK на живі
довідники-джерела; фактура має відтворюватись через 10 років без них
(GoBD). Рядки не редагуються після issue — інваріант коду і майбутній
constraint-тригер.

### fin_invoice_tax_totals — рекапітуляція

`(invoice_id, vat_rate, net, tax, gross)` — по одному рядку на ставку;
це блок «MwSt-Übersicht» у PDF і майбутня основа DATEV/ZUGFeRD.

### Оплати

Наявні fin_-таблиці операцій доповнюються зв'язком `invoice_id` +
`method` (`cash` \| `card` \| `transfer` \| `voucher`). Це дає
Tagesabschluss (день: готівка/карти по фактурах) — заміна ручного
касового журналу пілота і звірка з ранковим звітом термінала.

Дизайн звірено з еталонною фактурою джерельної системи (2026-08,
готель-пілот): рядки з колонками Gastname/Zi-Nr/Leist-Datum, оплати
всередині документа, підсумок Gesamtleistungen / Gastauslage /
Zahlungen / Debitor / offener Betrag, рекапітуляція 7%/19% таблицею
брутто-нетто-податок — модель фоліо/рядків покриває це один в один.
Друковані колонки Gastname і Zi-Nr додаються в шаблон рядка.

## 3. Правила обчислення

1. **Брутто-первинність.** Ціни зберігаються брутто; на рядку
   `net = money(gross / (1 + rate/100))`, `tax = money(gross − net)`.
   **Рекапітуляція рахується від суми брутто групи ставки**
   (net_group = money(gross_group / (1+r)); саме так рахує джерельна
   система пілота, і так звик її Steuerberater), тому на фактурі
   рекапітуляція може на ±цент відрізнятись від суми по рядках —
   це законно (Abschn. 14.5 UStAE), еталон — групова цифра.
   `fin_invoice_tax_totals` зберігає групові значення.
2. **`money()` з `@core/money` всюди** (AGENTS §3.9).
3. **Ставка — за service_date** рядка, не за датою фактури.
4. **Kleinbetragsrechnung** (§33 UStDV): брутто ≤ 250 € — дозволений
   спрощений шаблон без даних покупця; `is_small_amount` вмикає
   варіант шаблону. Ліміт — конфіг організації (чеського аналога нема —
   там вимкнено).
5. **Обов'язкові поля §14 UStG** у шаблоні: продавець+адреса,
   Steuernummer/USt-IdNr, покупець (крім small), номер, дата
   виставлення, період послуг (заїзд–виїзд), кількість+опис по рядках,
   нетто по ставках, ставка і сума податку, брутто. Плюс готельне:
   гість, номер кімнати, спосіб оплати, сплачено/залишок.
6. **Мова/локаль шаблону** — з організації (de-DE: формат чисел, дат);
   ISDOC генерується лише для чеських організацій, для DE — PDF
   (ZUGFeRD — окрема фаза, поля вже сумісні).

## 4. Потоки

- **Заїзд/проживання:** нічні lodging-рядки + послуги накопичуються у
  фоліо; екран фоліо = «рахунок гостя зараз».
- **Виставлення:** вибір фоліо (або його частини, або кількох фоліо
  одного дебітора) → знімок у fin_invoice_lines → номер із серії →
  PDF → рядки позначаються invoice_id.
- **Сторно:** нова фактура status=storno з рядками ×(−1), посиланням
  на оригінал і власним номером; рядки фоліо звільняються для
  перевиставлення.
- **Депозит/передоплата** (пілот не бере, система вміє): платіж без
  фактури → при виставленні рядок «Anzahlung erhalten» зменшує
  залишок; податково — за загальними правилами передоплат (Anzahlung
  оподатковується при отриманні — узгодити зі Steuerberater перед
  активацією фічі).
- **Звіти:** Tagesabschluss (оплати за день за методами),
  сніданковий/денний лист читають folio_items за service_date.

## 5. Фіскалізація (TSE) — обов'язкова для DE при готівці/картах

Еталонна фактура пілота несе рядок «Publickey: …» — TSE-підпис.
Правова база: §146a AO + KassenSichV — електронна система запису з
касовою функцією (а PMS, що приймає готівку на рецепції, нею є)
мусить: мати сертифіковану TSE, друкувати обов'язкові реквізити
белега, вміти **DSFinV-K-експорт** для Kassen-Nachschau і бути
**зареєстрованою у Finanzamt** (Meldepflicht через ELSTER, чинна з
2025). Наслідки для нас:

- інтеграція хмарної TSE (провайдер типу fiskaly SIGN DE) на потоці
  «оплата на рецепції» — до go-live німецького клієнта; безготівкові
  перекази поза касовою функцією TSE не потребують;
- поля TSE-підпису (serial, sig-counter, transaction, publickey) —
  у шаблоні белега/фактури;
- DSFinV-K — експорт журналу касових операцій (лягає на
  fin_folio_items/payments);
- питання переносу реєстрації каси пілота — до Steuerberater.

## 6. Що свідомо не робимо зараз

ZUGFeRD/XRechnung (до B2B-обов'язку 2027/28 — модель полів уже
сумісна); DATEV-експорт (фаза 2 — з fin_invoice_tax_totals це мапінг);
автоматичний POS-фід (ручні нарахування day-1); проформи (Angebot
друкується як пропозиція, не як фактура).
