## 0. Головне за одну хвилину

Виправлення попереднього раунду **справжні**: `tsc`, `npm run check` (≈40
самоперевірок + 15 гейтів), `build`, три i18n-гейти — усі зелені; мертвих таблиць

Але аудит знайшов **новий пласт**, якого раніше не бачили — і головне з нього
доведено не читанням коду, а живими запитами:

| Що | Доказ |
|---|---|
| Підтверджена бронь за **ціною 0** через масове редагування цін | живий ланцюг до `status=confirmed, total_price=0` |
| Готель B **перейменував і видалив** довідник готелю A | два логіни, HTTP 200, рядка в БД немає |
| Готель B **обнулив комісію** і видалив канал продажу готелю A | HTTP 200, у БД `commission_percent` 15→0 |
| Кнопка «Видалити» у журналі фінансів — **500 завжди** | операція лишається в БД |
| iCal-експорт на Postgres віддає **порожній календар** | доведено на справжньому PG: 0 проти 1 рядка |

Останній пункт — найважливіший методологічно: **уперше піднято справжній
Postgres** (усі попередні аудити писали «живий PG не піднімався»). Виявилось, що
цілий клас функцій, які на SQLite працюють, на проді мовчки повертають порожнє.

## 1. Чому SQLite-перевірки вводили в оману

`scopeToTenant()` (`core/db/postgres.ts:162-170`) на **кожному** checkout з'єднання
ставить `app.organization_id` і `app.public_token` у значення з ambient-контексту,
а якщо його немає — у **порожній рядок**. RLS-політики звіряють рівність із
непорожнім значенням, тому хендлер, який не викликав `runWithOrganization` або
`runWithPublicToken`, на Postgres бачить **нуль рядків** — без помилки.

Доведено прямим тестом на піднятому PG (роль `alisio_app`, як на проді):

```
рядків у ical_channels:                        1
роль застосунку, порожній контекст:            0   ← так працює exportIcal
роль застосунку, правильний орендар:           1   ← контроль
```

Наслідок: усе нижче з позначкою `[PG-порожньо]` **на SQLite працює, на проді ні** —
тому й не помічалось. Дзеркально, `[SQLite]` означає протилежне: на проді прикрито
RLS, а локально/в демо відкрито.

## 2. P0 — критичне

### 2.1 Бронь за ціною 0 через масове редагування цін ✅живий ланцюг
Порушує інваріант AGENTS.md §3 п.17 («Ціни, якої немає, не існує»).

`price-calendar.repo.ts` (`bulkUpdatePrices`): `input.base_price ?? existing?.base_price ?? 0`.
Ціна ніде не валідується — ні тут, ні в `bulk.handlers.ts:22-27` (перевіряються лише
`unitTypeId`/`dateFrom`/`dateTo`). UI шле `base_price: undefined`, коли поле лишили
порожнім, бо його placeholder — «**Не змінювати**» (`pricing/page.tsx` BulkEditModal).

Досяжний з екрана сценарій: «Ціни → Масове редагування» → діапазон дат, де цін ще
немає → заповнити **лише** «Мін. ночей» → Зберегти.

```
PUT /api/pricing/bulk {unitTypeId, dateFrom:2027-03-01, dateTo:2027-03-05, min_stay:2}
  → 200 {"success":true,"updated":5}          у БД: 5 рядків base_price = 0
POST /api/pricing/quote на ці дні
  → total:0, missingDays:0, hasPricing:TRUE   ← інваріант 17 не спрацьовує: ціна «є»
POST /api/bookings
  → 201; у БД: total_price=0, status=confirmed
```

Гейт `check-price-source` це не ловить — тут не друге джерело ціни, а нуль у єдиному.

Другий бік того самого: `reservations.handlers.ts:213-216` пише `totalPrice || 0` без
серверної валідації. Захист інваріанта 17 живе **лише** в `BookingForm` — будь-який
інший виклик `POST /api/bookings` створює нульову бронь. Поруч, у тому ж INSERT,
для валюти вже стоїть строга відмова (`if (!currency) return serverError`).

**Фікс:** не створювати новий рядок календаря без ціни (пропускати дату), або
вимагати `base_price` у хендлері при створенні; плюс серверна перевірка ціни в
`createReservation`; плюс `.check.ts`.

## 6. Межі цього аудиту

- Postgres піднято і використано для доказу класу RLS, але застосунок під ним **не** проганявся повністю — частина `[PG-порожньо]` доведена механізмом (тест RLS), а не HTTP-запитом до кожного хендлера.
- Крос-тенантні експлойти виконані на SQLite (дефолт розробки). На Postgres їх має блокувати RLS — але саме двошаровість вимагає AGENTS.md, і `owned.repo.ts` існує рівно для цього.
- Математика фінансів (ISDOC, §14 UStG, VAT-снапшоти) — перевірено підключення, не числа.
- Планувальник cron поза git — чи `/api/cron/*` реально викликаються, з репозиторію не видно.
- Мобільні екрани й маркетингові сторінки — вибірково.
