# Заведення нового готелю — процес і скільки він триває

Записано з репетиції 2026-08-28: порожня база → готель «Hotel Aurora»
(hotels/demo-hotel.json) → бронювання через API → фактура RE2026-0001.
Це чернетка процесу для справжнього другого готелю: числа виміряні, а не
обіцяні.

## Що таке «завести готель»

Один файл. `hotels/<slug>.json` описує організацію, обʼєкт, податкові
ставки, серії фактур, категорії, типи номерів з цінами, номери, послуги,
канали і **приймальні перевірки цін** (без них файл не проходить
`check-hotels`). Шаблон — `hotels/_example.json`; живий приклад —
`hotels/demo-hotel.json`.

Застосовувач (`scripts/apply-hotel.mjs`) сам створює організацію, якщо її
немає, і сам друкує одноразовий пароль власника. Він ідемпотентний і нічого
не видаляє: файл описує стан, а не список дій.

**Три поля без дефолтів** (В1, К16): `organization.currency`, пояс
(`organization.timezone` або країна з одним поясом) і `property.propertyType`
— рід житла. Це не формальність: валюта каже, що означає кожна сума, пояс —
де проходить межа доби для дат, якими торгує канал, а рід житла — за що
менеджер каналів виставить рахунок (готельна група тарифікується за обʼєкт,
оренда — за юніт). Вгадане тут значення нічого не ламає видимо; воно просто
виявляється неправильним місяцем пізніше. Без будь-якого з трьох файл не
проходить `check-hotels`, а заведення відмовляє названими словами.

## Шлях на сервері (справжній онбординг)

1. Написати `hotels/<slug>.json`. На репетиції на це пішло ~10 хвилин;
   помилки ловляться ще локально: `node scripts/check-hotels.mjs`.
2. `git push` → бета застосовує файл сама (apply_hotels у deploy.sh),
   конвеєр беты ≈ 8–10 хв. Потім beta → main, і прод застосовує так само.
3. Пароль власника друкується ОДИН раз — у лозі деплою (крок apply hotels).
   Зайти ним і одразу змінити. Це відома вада процесу: пароль видно всім,
   хто бачить лог Actions, тож перший вхід і зміна пароля — не «колись
   потім», а частина заведення.
4. Демо-проживання (`seed-demo-stays.mjs --all`) деплой сіє сам — лише
   поза продом, вигаданими гістьми на example.com.

## Виміряно на репетиції (стенд AGENTS §7, порожня база)

| Крок | Команда | Час |
|---|---|---|
| База з нуля: schema.sql + 47 міграцій + роль `alisio_app` | `psql -f …` у циклі | ~3 хв |
| Застосувати готель (13 номерів, 3 типи, ціни, послуги, серії) | `node scripts/apply-hotel.mjs hotels/demo-hotel.json` | ~15 с |
| Приймальні перевірки цін (у складі apply) | — | входить |
| Демо-проживання | `node scripts/seed-demo-stays.mjs hotels/demo-hotel.json --env beta` | ~5 с |
| Логін власника → бронь через `POST /api/bookings` → фактура `POST /api/invoices/custom` | curl | ~1 хв |
| **Разом машинної роботи** | | **≈ 4–5 хв** |
| Разом із написанням файла готелю | | **≈ 15 хв** |

На сервері кроку «база з нуля» немає (вона вже стоїть), тож реальний
онбординг = написати файл (~10 хв) + два цикли конвеєра (бета, потім прод,
≈ 10 хв кожен) + перший вхід власника.

## Що довелося робити руками, крім файла

Нічого. Організація, власник, пароль, категорії, ціни, номери, серії
фактур, джерела бронювань — усе з файла. Дві речі, які лишаються ручними
за задумом:

- перший вхід власника і зміна одноразового пароля (див. вище);
- рішення про демо-дані на проді — їх там не буває (сід відмовляє проду
  двічі: у deploy.sh і в самому скрипті).

## Перевірити після заведення

```bash
./deploy/list-tenants.sh beta          # організація на місці, лічильники ненульові
./deploy/smoke.sh beta                 # health, логін-401, головна
```

І очима: календар показує демо-заїзди, бронь створюється, фактура
нумерується СВОЄЮ серією з файла (на репетиції — RE2026-0001).
